# 创建规则：搭建你的项目全局规则

## 输入：先接通参数

本技能接受**最多两个可选路径**，并用它们来选定你的车道（lane）。读取传入的内容，按内容给每个路径分类：
- `$path1`：第一个路径（如有）。
- `$path2`：第二个路径（如有）。

| 传入的路径是…… | 车道 | 把它用作 |
|---|---|---|
| **PRD**（意图、做什么/为什么，来自 `plan-create-prd`） | 全新项目 | 产品上下文（"这是什么"），**不是**技术规则的来源 |
| **架构/规格文档**（怎么做，来自 `plan-architecture`） | 全新项目 | 你的规则所依据的技术决策（如果架构被折叠为 `## Architecture` 章节，它可以是*与 PRD 同一个文件*） |
| **codebase-analysis 文档**（大型仓库的 `/prime-codebase` + 子代理扇出） | 存量项目 | "现状是什么"的来源 |

**根据给你的内容挑选车道：**
- **全新项目**：如果传入了 PRD 和/或架构路径，或工作区只是一个空脚手架：从**架构决策**（`$path2`，或 `$path1` 如果决策就住在那里）推导**应该是什么**。
- **存量项目**：如果没有传入路径，或传入了 codebase-analysis 路径：从分析文档（如果传入了）推导**现状是什么**，否则从**本次对话中已加载上下文的代码库**推导。

> **存量项目但还没加载上下文？** 如果没有传入路径且本次对话还没加载过代码库上下文，先运行 **`/prime-codebase`**（或提议运行它），这样你才能从真实文件推导，然后再继续。绝不凭空发明规则。

## 什么是全局规则（30 秒简介）

你的全局规则——**`CLAUDE.md`**（Claude 原生）或 **`AGENTS.md`**（开放的跨工具标准）——是**常驻开启的指路文档**，每个任务都会读取。有四类内容配得上这个常驻位置：
1. **代码库地图** —— 重要的目录/文件，每个配一行 *它是什么 + 为什么放在这里*。
2. **基本规则（ground rules）** —— 本项目遵循的*具体约定*（你如何做类型安全、你的错误哲学、你的 git 工作流）。陈述选择本身，而不是口号。
3. **AI 助手应该自己运行的命令** —— 真实的 lint / 类型检查 / 测试 / 工具 CLI（带它们的标志），这样它就能检查自己的工作。（不是斜杠命令——那些是*技能*。）
4. **工作原则（AI 助手转向）** —— 你希望 AI 助手在这里*如何运作*：它的思考/推理姿态（非平凡工作前先计划、有歧义时询问而不是猜测、保持范围紧凑）以及你坚守的工程原语（快速失败、显式错误、单一职责、最简单的可行方案）。**这些不在代码里——由你陈述。** 它们是"从代码库推导"永远无法产出、且除非你明确说明否则 AI 助手不会可靠遵循的部分。

**一切都是组合。** 规则、参考资料和技能只是 AI 助手需要时加载的 markdown——所以上述任何内容都可以常驻开启 *或* 住在按需加载的 `references/` 文档 *或* 住在技能里；由你决定每块内容住在哪里。不是每个任务都需要的所有内容**按需**加载，或属于每个任务的**计划**——而不是这里。

## 两种情况，同一种动作

全局规则编码的是**技术**事实——所以你要从技术决策推导它们，绝不从产品规格推导：

| 你拥有…… | 从……推导规则 | "事实"是…… |
|---|---|---|
| **全新项目**，一个新项目，基本是脚手架 | 你的**架构决策**（你和 AI 敲定的技术"怎么做"），作为 `$path2` 传入 | *应该是什么* |
| **存量项目**，一个没有 AI 层的现有代码库 | 你**预热的代码库**（`/prime-codebase`），或对大型仓库传入的 **codebase-analysis** 文档 | *现状是什么* |

> **全新项目备注：** 你的规则来自你的**架构决策**（规格），不是 PRD。流程：与 AI 讨论你要*做什么*并捕获为 PRD（`plan-create-prd`），然后用 `plan-architecture` 敲定**架构**（技术栈、模式、目录结构、约定）。本技能从*这些*决策推导规则。PRD 捕获的是*产品*（做什么/为什么）：有用的上下文，但技术规则不住在那里。

> **存量项目备注：** 本技能**不**为你探索代码库。先预热：运行 **`/prime-codebase`**，让结构、关键文件和约定加载进本次对话，然后不带路径运行本技能。（大型仓库？可选：扇出几个内置子代理并行探索各区域，汇总一份简短的 `codebase-analysis.md`，改传那个路径。）本技能打包的是 *derive → extract → seams → prune → check*（推导 → 提取 → 接缝 → 精简 → 检查）步骤，不是探索本身。

> **运行前——保护任何现有规则。** 如果项目已有 `CLAUDE.md` / `AGENTS.md`，**先复制或重命名它**（例如 `CLAUDE.md.bak`），这样本技能不会覆盖你想保留的东西。更好的是，**把它作为输入喂进来**——让技能指向它（"先读取我现有的 `CLAUDE.md`"），这样推导就能*建立在*已有的内容之上，而不是从头开始。

## 必读（先做这个）——并挑选文件

**首先，这个项目用哪个规则文件？** 检测它，然后读取匹配的指南（不要依赖快照）：
- **`CLAUDE.md`**（Claude Code 的原生文件；Qoder/Cursor 同样读取根级 CLAUDE.md）→ 记忆 + 最佳实践参考：
  https://code.claude.com/docs/en/memory · https://code.claude.com/docs/en/best-practices
- **`AGENTS.md`**（开放的跨工具标准，几十种 AI 助手会读取）→ AGENTS.md 规范：https://agents.md
- **两者都在？** 通常共享内容住在 **`AGENTS.md`** 里，`CLAUDE.md` 只有一行——`@AGENTS.md`——这样 Claude Code 会自动加载 AGENTS.md，且只有一个事实来源。这种情况下，写入 AGENTS.md。
- **都没有？** 纯 Claude-Code 项目用 `CLAUDE.md`；多工具团队用 `AGENTS.md`。

无论哪种，内容 + 结构都约有 90% 相同——下面的所有内容都指"**你的规则文件**"，而不是某家厂商的。使用下面列出的结构（它同样可以当作 AGENTS.md 用）。

## 方法论（内化它）

- **什么常驻开启：** **地图** + **基本规则**（具体约定）+ **工作原则**（AI 助手转向）。所有*项目级、每个任务*都为真的事情。
- **工作原则是被*引导出来*的，不是推导出来的。** 地图和基本规则来自代码/决策；工作原则来自**你**——所以要**问**："AI 助手在这里应该怎么工作——计划优先？编码前澄清？范围纪律？你坚守哪些工程原语？" 只保留那些真正*改变行为*且反映*你*立场的——而不是模型已经在遵循的泛化说教。
- **四个去向** —— 对每一行候选内容归类：
  - **保持常驻开启** → 地图 / 基本规则。
  - **推给按需加载** → 反复出现但属于任务*类型*特定的模式 → 按需加载的参考资料（Claude Code 上是 `.claude/references/<topic>.md`；Qoder 项目可用 `.qoder/rules/` 或 `docs/ai/references/`；你的工具找得到的任何地方——例如 `.agent/`——它只是 markdown）或一个技能。
  - **移进计划** → 任务特定的"下一步建什么"内容 → 它从来就不是规则。
  - **删除** → 冗余内容，或模型已经在遵循的口号（"写干净代码"、"KISS/DRY"）。
- **陈述选择本身，而不是口号：** "用 `z.infer` 推导类型"，而不是"类型安全至关重要"。
- **存量项目 = "现状是什么"，不是"应该是什么"：** 每条规则都必须指向证明它的文件；如果指不出来，就别写。理想化的规则会让 AI 助手与代码库对抗。
- **精简：** 不要臃肿到吞噬上下文或让 AI 助手开始无视自己的规则。没有魔法行数——任何删掉也不会导致错误的内容都砍掉。

## 工作流

### 1. 读取输入
- **全新项目：** 读取你作为 `$path2` 传入的**架构/规格文档**（或 `$path1`，如果架构就在那里）：技术栈、模式、目录结构、约定、安全选择，加上任何脚手架文件。*（作为 `$path1` 传入的 PRD 是产品上下文：读它是为了**做什么**和为什么，不是技术规则。）* 没传路径但工作区是全新脚手架？索要架构文档，或先用 `plan-architecture` 敲定决策。
- **存量项目：** 从本次对话中**已加载上下文的代码库**（来自 `/prime-codebase`）推导；或者，如果传入了 `codebase-analysis.md` 路径，读取它（连同它的 file:line 引用）。无论哪种都抽查实际代码。没预热也没传路径？先运行 `/prime-codebase`。
- **如果规则文件已存在：** 先读它，把它当作起点——并确保它已备份（见上面"保护任何现有规则"），这样你手写的内容不会丢失。
- 阅读上面的最佳实践文档。遵循本技能列出的结构。

### 2. 推导根级 `CLAUDE.md`
用来自输入的内容填充模板的各章节：
- **这是什么** —— 一段概述 + 一行技术栈。
- **架构地图** —— 重要的目录/文件树，每个一行是什么/为什么。
- **基本规则** —— 具体约定（全新项目：在你的**架构规格**中定下的，不是 PRD；存量项目：*在代码中观察到的*，每条可追溯到文件）。
- **工作原则（AI 助手转向）** —— **询问用户**（这无法从代码推导）：AI 助手在这里应该如何运作？捕获思考/推理姿态（计划优先、澄清而非猜测、范围纪律、对照*真实*测试套件验证）+ 他们坚守的工程原语（快速失败、显式错误、单一职责、最简单的可行方案）。陈述项目的*实际*立场；保持精简。
- **命令** —— 你真正运行的那几个（安装 / 测试 / 类型检查 / lint / 运行）。
- **按需加载的指针** —— 细节需要时从哪里加载。
不要把 PRD 或分析文档倾倒进来。链接到它们。

### 3. 提取按需加载的上下文
把反复出现、任务类型特定的模式抽到项目声明的按需加载参考资料目录（Claude Code 为 `.claude/references/<topic>.md`，Qoder 项目为 `.qoder/rules/` 或 `docs/ai/references/<topic>.md`）**占位文档**里（每份一段，不是完整文档）。测试：*每次碰那个区域都会反复出现吗？* → 指南。一次性 → 留在源文档里。

### 4. 找到接缝
添加一个简短的**"新代码去哪里"**章节——新工作插入的接口/文件夹。这是让 AI 助手 *扩展*代码库而不是外挂的关键。（全新项目：接缝是从架构*设计*出来的，不是发现的。）

### 5. 精简
初稿总是太大。删除泛化建议、重述的默认值，以及任何指不出证据的内容。应用逐行测试：*删掉这行会导致错误吗？不会就砍掉。*

### 6. 报告
- 创建/更改的文件。
- 3–5 行概述：`CLAUDE.md` 里放了什么、为什么。
- 什么被推给了按需加载的上下文（以及在哪里）。
- 下一步：规则已就绪——启动第一个 PIV 循环。

## 质量检查

- ✅ 根级 `CLAUDE.md` 是**地图 + 基本规则**，不是文档或 PRD/分析副本。
- ✅ 每条基本规则都是**具体选择**（存量项目：可追溯到文件）——没有口号。
- ✅ 存在**工作原则 / AI 助手转向**章节——*从用户那里引导出来的*（计划 / 澄清 / 范围姿态 + 工程原语），精简且能改变行为，不是泛化填充。
- ✅ 反复出现的任务类型细节住在按需加载的参考资料（`.claude/references/` 或 `.qoder/rules/`），不在常驻开启区。
- ✅ 精简到没有任何内容能不付"租金"就占位。

## 备注

- 规则**会演变** —— 随着项目成长和重大模型发布后重新审视 `CLAUDE.md`，并在合并前运行 `/rules-check-drift`，这样地图永远不漂移。
- 全新项目：在用 `plan-architecture` 敲定架构后运行（如果你为产品写了 PRD，也在 `plan-create-prd` 之后）；把这些路径作为 `$path1`（PRD）和 `$path2`（架构）传入。存量项目：在 `/prime-codebase` 之后运行，或在大仓库扇出产出你可以传入的 `codebase-analysis.md` 之后运行。
