# 指导层

三个文件，三种不同的工作。这个拆分本身就是全部的教义。

几乎每个人都把这一切塞进一个约定文件里，然后奇怪为什么 agent 会漂移、和自己的约束争吵、或编辑那条碍事的规则。

| 文件 | 拥有 | 示例 |
|---|---|---|
| **约定**（`CLAUDE.md` / `AGENTS.md`） | 任何项目都有的约束和约定 | *用 Bun 不用 npm。所有 SQL 都在 `repository.py` 里。* |
| **`FACTORY_RULES.md`** | agent *无人监督*时如何运作 | *每个 PR 最多 500 行。永远不要为了让它通过而改测试。碰受保护文件立即拒绝。* |
| **`MISSION.md`** | 正在建什么，以及刻意排除什么 | *不做支付。不做移动应用。不做第二个渠道。* |

## 放置测试

对每条规则，按顺序：

1. **即使由人类来做这个工作，你也会写下这条吗？** → 约定文件。
2. **它只因为没人看着才存在吗？** → `FACTORY_RULES.md`。
3. **它是关于产品是什么和不是什么吗？** → `MISSION.md`。

### 三个边界案例，已解决

- **"每个 PR 最多 500 行。"** 感觉像代码约定。但仓库里没有任何人类受它约束——它存在纯粹是因为无人监督的 agent 否则会交付没人能审的 3,000 行。**工厂规则。**
- **"提供商 X 是唯一的 LLM 提供商。"** 看起来像是约定文件里的技术栈条目。它要防止的失败是范围漂移，而不是不一致。**任务不变量。**
- **"每个端点都保持已认证。"** 真的住在两个文件里，这种重复是有意的：`MISSION.md` 把它作为产品真相持有，`FACTORY_RULES.md` 把它作为自动拒绝触发器重申。**在拒绝时刻读取的文件必须包含这条规则。** 出于机械原因的重复没问题；出于偶然的重复就是文件漂移的方式。

### 如果约定文件已存在

它通常存在，而且通常同时承担着三项工作。**拆分它，不要替换它。** 对里面每一行跑一遍放置测试，把只属于工厂的规则移到 `FACTORY_RULES.md`，把产品真相移到 `MISSION.md`。剩下的是约定文件，而且会比原来短。

这个拆分往往是对既有仓库做出的最有用的单次编辑，无论用户是否真的开启 cron 都有回报：一个只装约定的约定文件，对交互式工作也是更好的约定文件。

### 如果 CI 已存在，写门之前先读它

注意到 `.github/workflows/` 存在不等于读过它，而之前只发生了前者：某次测试运行只凭"有 CI"就通过了 Phase 0，保护了 `.github/`，却从未打开过文件。CI 已经断言了合并门正要从头重新实现的东西，没人注意到。

所以打开它。两样东西会出来：

- **你不用发明的命令。** CI 为 lint、类型和测试运行的任何东西，都是 `harness.config.json` 中 `static` 和 `unit` 的经过测试的答案。复用它，而不是写一个与前者漂移的第二个定义。
- **已经存在的断言。** 如果 CI 强制了某种真实的东西——依赖禁令、覆盖率下限、schema 检查——那就是你已经拥有的一级阶梯。说出来，把时间花在独立线上方的阶梯上。

然后说明哪个是权威。工厂的门决定合并，所以如果 CI 和门不一致，门赢——但 CI 一直红着而工厂愉快地合并，是有人会绊倒的矛盾。要么让 CI 指向 `FACTORY_VALIDATE_CMD`，让定义只有一个，要么写下来"这里的 CI 仅供参考"。

## 关键属性

> **agent 不能修改评判它的规则。**

三个文件都进受保护清单。修改其中任何一个的 PR 在任何其他评估之前被自动拒绝，验证器从**基础分支**读取这三个文件，而不是从被审的 PR 里读。没有这个顺序，PR 可以削弱自己的规则书，然后对着被削弱的版本通过。

这是把一个"会写代码的东西"变成"你可以放心不管的东西"的唯一属性。

## 受保护清单

任何碰到这些的 PR 直接被拒绝，没有修复尝试，底层 issue 升级——因为碰它们意味着工厂误解了范围。

用所有这些做种子，然后问还有什么：

- **治理：** 上面三个文件。
- **CI 和仓库配置：** `.github/` 下的一切、工作流定义、issue 和 PR 模板、CODEOWNERS。
- **基础设施：** Dockerfile、compose 文件、`deploy/` 或 `infra/` 下的一切、systemd 单元、平台配置（`fly.toml`、`render.yaml`、`Procfile`）。
- **密钥和认证：** `.env` 及其所有变体、任何持有 token 的 agent 或工具配置文件、任何名字像凭据的东西、以及定义哪些端点受保护的模块。
- **安全不变量：** 限流常量及其执行路径、CORS、CSRF、认证中间件。

### 防止最严重事故的预检

在**任何**产生 commit 的工作流之前，运行：

```bash
git check-ignore -v <每个可能持有 token 的配置文件>
```

**空输出意味着你的下一次运行会发布你的密钥。** PR 创建步骤里的 `git add -A` 会把没被忽略的东西扫进来，在公开仓库上那是发布，不是你能收回的错误。事后轮换是清理，不是修复。

把检查加为工作流中的一个节点，而不是加在人类读的清单里的一行。

## 写 `MISSION.md`

### 它从 PRD 派生，不是从零写起

`MISSION.md` 是 PRD 压缩到 agent 必须遵守的部分。不要从空白文件开始，也不要整篇粘贴 PRD。做映射：

| PRD | `MISSION.md` |
|---|---|
| 问题、为什么重要 | 开头段，保持简短 |
| 用户 | 一行，因为 E2E 路径就是按它演出的 |
| MVP 范围、能力领域 | **范围内** |
| **非目标** | **永远范围外**（见下面的分类） |
| 成功指标 | 一次合并的变更最终要推动什么 |
| 任何标着 TBD 的东西 | **不要**把它作为规则带过来。它变成 `.factory/decisions.md` 里的一条——由工厂提议、在合并处持有、只回答一次。在这里放一个笼统的 `needs-human` 触发器，正是让诚实的 PRD 阻塞它下游每个 issue 的方式 |

**关键分类："现在不做"不是"永远不做"。** PRD 的非目标通常两者混杂，因为 PRD 是为一季度让团队保持专注而写的，没人需要精确区分——读它的人类自然知道。agent 不知道。任何记成范围外的东西都会在 triage 被永远拒绝，包括下季度它成为路线图的时候。

逐个走非目标，分成三堆：

- **永远不。** 进 `MISSION.md`。
- **还没到时候。** 进 backlog，绝不能出现在 `MISSION.md` 里。
- **永远不，而且它是属性而不是功能。** 那是硬不变量，进下面的不变量节加上 `FACTORY_RULES.md`。

如果分完第一堆少于五条，清单太薄了。回到访谈去要更多。

### 干活的的两个章节

两节做真正的工作，其中一节是大家跳过的那节。

**范围内** —— 工厂可以构建的能力领域。短。triage 按它接受。

**永远范围外** —— 靠它吃饭的一节。这是 agent 识别"一个貌似合理、论证充分、容易实现的功能请求是漂移而不是好主意"的方式。没有它，每个请求都说得上在范围内，因为几乎每个功能单独看都能自圆其说。

目标至少五条，而且要是一个理性的人真的会提的那种：

> 不做支付或订阅。不做移动或桌面应用。不增加内容来源。不向第三方提供公开 API。不做社交功能——不评论、不点赞、不分享。不提供替代输入模式。

**硬不变量** 与范围外条目不同，值得有自己的章节。范围外是*你不会添加的功能*。不变量是*不能被编辑的属性*：一个限流、一个认证要求、一个隐私保证、一个单租户假设。一个论证充分地要求改变不变量的 issue，在 triage 就被作为安全问题拒绝，而不是被辩论。

## 写 `FACTORY_RULES.md`

覆盖这些章节。templates 目录里有更完整的骨架。

1. **Triage 规则** —— 接受什么、拒绝什么、交给人类什么。对模糊性偏向拒绝并明确说出来：一次错误拒绝花一条评论，一次错误接受花一个错误 PR 和一次验证循环。
2. **实现规则** —— 绝对禁令。永远不要为了通过而改测试。永远不要碰受保护文件。永远不要在没有 PR 正文理由的情况下加依赖。永远不要超过大小上限。永远不要超出 issue 要求去构建。
3. **自动合并的质量门** —— 条件枚举清单，每一条都必须为真。标明哪些在代码里强制执行。
4. **自动拒绝触发器** —— 无法增量修复的失败，所以 PR 被关闭而不是被打回。
5. **升级** —— 什么让它停下来要人类，以及人类如何清除。
6. **成本与吞吐限制** —— 批大小、尝试上限、并发、优先级顺序。
7. **关注点分离** —— 留出集规则，写出来：验证器可以读什么、绝不能读什么。
8. **沟通风格** —— 工厂怎么写评论。以决定开头，按章节号引用规则，保持中立，留下申诉路径，绝不承诺未来行为。
9. **这个文件如何变更** —— 只能人类提交。它在受保护清单上。

### 为什么章节号重要

要求工厂在它发的每条评论里**按章节号引用驱动决定的规则**。两个原因，都很实际：

- 收到带规则引用的拒绝的提交者可以读那条规则并申诉。没有引用的拒绝读起来像武断。
- 你得到自己规则书的使用痕迹。从未被引用的规则要么从未触发，要么从未被读，两种都值得知道。

工厂能产出的最好产物不是合并的 PR。而是一个 issue：系统读了 bug 报告，发现真正的根因在自己的仓库之外，注意到修复它需要碰受保护文件，引用使那成为拒绝的两条章节，拒绝了工作，并留下申诉路径。

**一个自主系统正确地什么都没做**——这就是指导层买来的东西。
