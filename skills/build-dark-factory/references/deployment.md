# 部署

组件 3 是最容易构建、也最容易跳过的部分。跳过它，你建的不是工厂，而是一个多走几步的 PR 生成器。

> **合并即发布，真实用户会拿到这份代码。**

如果合并没有产出可运行的应用，合并之后的一切都不真实，验证装置一直在证明的是关于"没人运行过的软件"的事情。

---

## 悄悄杀死工厂的陷阱

> **GitHub 不会对使用默认 `GITHUB_TOKEN` 提交的 commit 触发工作流。**

这是文档化的行为，目的是防止工作流无限递归，也是自主循环悄然死掉的最常见方式：

1. agent 用默认 token 提交并合并。
2. 你的部署工作流有 `on: push` 触发器。
3. 它从不触发。
4. 没有报错。没有日志。没有告警。PR 持续合并，网站持续提供旧构建。

两个修复：

- **以 GitHub App 身份认证**（或使用 PAT）来提交那些应该触发下游工作流的 commit。
- **轮询而非推送。** 按定时器检查分支的部署流程不可能被悄悄跳过，因为它的运行不需要任何东西先触发。响应慢一些，但不可能漏掉。

对工厂来说，轮询通常是更好的权衡：这是一个以"没人看管"为定义属性的系统，所以优先选择大声失败的机制，而不是静默失败的机制。

## 同一份文档里的另外两条

- **定时工作流只从默认分支运行。** 放在特性分支上的 cron 什么都不做，永远如此，且没有任何警告。
- **在公开仓库上，GitHub 会在 60 天无仓库活动后禁用定时工作流。** 安静的工厂会因为安静而被关掉——然后一直关着，看起来和"它没什么可做的"一模一样。

两条都值得写进 `FACTORY.md`，因为它们都表现为"工厂停止工作了但我看不到任何错误"。

## 部署策略

选一个最简单的、能回滚的。

| 策略 | 怎么做 | 回滚 | 适合 |
|---|---|---|---|
| **蓝绿** | 构建非活跃的那一色，做健康检查，翻转代理上游，停掉旧的 | 翻回去；旧构建还是热的 | 长期运行的应用，且你掌控主机 |
| **平台部署** | 推送到替你构建和切换的平台 | 平台自己的回滚 | 你不想自己管主机 |
| **容器标签切换** | 构建、打标签、按新标签重启 | 重新打回上一个镜像的标签 | 已经容器化 |
| **静态发布** | 构建产物，发布到 CDN | 重新发布上一个构建 | 纯前端 |

无论怎么选，**没有变化时必须安全地 no-op**。无人值守的部署循环运行的次数远多于实际部署的次数，一个每次 tick 都干活的部署路径，最终会在某个什么都没发生的 tick 上造成破坏。

### 健康检查是部署的一部分，不是锦上添花

永远不要把流量切到一个没通过健康检查的构建上。在无人值守系统里，这是真实用户前的最后一道门，也是合并之后唯一运行的那道门。

---

## 接线到循环里

部署在合并的下游，应该和所有其他东西一样从同一个地方可观测：

1. 合并发生（squash，保持历史可读，回滚就是一次 revert）。
2. 部署触发——通过 App 认证的推送，或通过轮询。
3. 健康检查把守流量切换。
4. **结果在工厂能读到的地方可见。** 一个状态端点，一个定时测试可以检查的部署日志。

最后一点在 4 级时很重要。如果定时综合测试能读到已部署应用的实时健康状态，它就能在部署损坏时自己提 issue——循环就这样闭合，无需人类先注意到。

---

## 该告诉用户什么

- **循环直到陌生人能看到变化才闭合。** 在那之前的一切都只是 PR 生成器。
- **优先选择大声失败的机制。** 轮询优于推送触发，健康检查优于想当然，显式标记优于"没有错误"。这和"空不是通过"是同一个原则，应用到基础设施上。
- **在无人值守之前决定回滚方案。**"我会向前修复"是有效答案，但它必须是答案，而不是事故过程中才发现的。
