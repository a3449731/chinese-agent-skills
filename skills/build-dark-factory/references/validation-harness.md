# 验证装置（validation harness）

这是组件 5，它占大部分工作，而且它是唯一决定其他四个是否产出了值得保留的东西的组件。

---

## 运行器期望你构建什么

如果你用 `templates/runner/`，先读这个。两个用这个技能建过工厂的人都从 `config.sh` 里一个默认字符串推断出整个布局，其中一个人不得不读运行器的源码才弄明白一个检查的输出是怎么到达门的。他们俩都不该需要那样。

**`templates/harness/` 是这一切的工作骨架**——`ci.py`、`appproc.py` 和 `e2e.py`。复制它、运行它，然后删掉 `e2e.py` 里的每条断言，写你自己的。它开箱即满足下面的契约，所以你在编辑一个已经通过的东西，而不是在调试管道的同时还要决定"工作"意味着什么。

**契约是四件事。**

**1. 一个单一入口点，在 `config.sh` 里命名。**

```bash
FACTORY_VALIDATE_CMD="${FACTORY_VALIDATE_CMD:-python harness/ci.py}"
FACTORY_VALIDATE_QUICK="${FACTORY_VALIDATE_QUICK:-python harness/ci.py --quick}"
```

`harness/ci.py` 是**约定，不是要求**——指向 `make check`、`npm run gate`、`./scripts/validate.sh`，什么都行。重要的是一个命令跑整个门。与约定配套的布局：

```
harness/          the checks. The builder CAN read and run these
  ci.py           the entrypoint: runs everything, prints markers, exits non-zero on failure
.factory/
  holdout/        assertions the builder is BLOCKED from reading (--disallowedTools)
  locks/          thresholds and floors a human set. Protected
  runs/           per-run artifacts. Gitignored
```

**2. 它必须为每个 RAN（真的跑了的）检查族打印一个正向标记**，而且标记必须匹配 `config.sh` 里的 `FACTORY_REQUIRED_MARKERS`。`APP_STARTED` 和 `E2E_PASSED` 不可商量。要数量，不只是名字：

```
APP_STARTED port=8080
E2E_PASSED steps=11
HOLDOUT_PASSED scenarios=2 assertions=30
MUTATIONS_TOTAL=7
MUTATIONS_CAUGHT=7
GATE_OK
```

**3. 软件坏了时它必须非零退出。** 门读标记，但退出码是实现节点自己 `--quick` 运行看到的东西。

**4. 追加契约，就是咬人的那个。** 运行器把 `guard.py` 的输出写进该次运行的 `gate.log`，然后把你 validate 命令的输出**追加**到同一个文件。`gate.sh` 对合并日志断言每个必需标记。两个后果：

- `PROTECTED_OK` 来自 guard，不是来自你。不要自己打印它。
- 如果你的入口点截断或重定向覆盖那个日志而不是写 stdout，guard 的标记会消失，每个门都会因为与你的代码无关的原因失败。**打印到 stdout，让运行器做管道。**

**`--quick` 是真实的义务，不是装饰。** 实现节点工作时在自己身上跑它，所以它必须快，而且必须是严格子集——绝不检查完整运行没有的。它按定义在 agent 的优化循环内，这正是完整门之后独立重跑一切的原因，也是下游没有任何东西信任 `--quick` 说了什么的原因。

**不要让构建者编辑装置。** `factory/guard.py` 在受保护清单上播种变异集，但 `ci.py` *就是*"工作"的定义——能编辑自己裁判的构建者能让任何声明为真。保护 `harness/**`，把合法的覆盖率增长路由到你正常的测试目录。

---

整个东西依靠的规则：

> **agent 必须像最终用户体验它那样验证应用。**
> 不是"测试通过"。而是当一个人用它的时候，东西是不是真的行。

在暗工厂里没人做手工测试，按定义。所以人类会执行的每个检查都必须作为 agent 能跑的东西存在——而且关键是，作为 agent 不能在不做工作的情况下悄悄满足的东西存在。

## 为什么"多写测试"是错的直觉

编码 agent 针对它能看到的信息优化。给它一个可见的测试套件和足够多的尝试，它会把这个套件弄绿。它是否让*软件*正确是另一个问题，而且随着代码库增长两者分道扬镳。

这是被测量过的，不是民间传说。关于长时程编码 agent 奖励黑客的工作，给 agent 评两次分——一次在它能读的可见套件上，一次在一个测试相同需求*组合在一起*的留出套件上。这两个数字之间的差距就是分数里有多少是真实的。值得内化的已发表发现：

- **差距随代码规模急剧扩大。** 大约每个数量级行数差几十个百分点。小任务上可见分数是不错的代理。大任务上它可能达到每个可见测试都是绿的、每个留出测试都是红的程度。
- **加更多测试并不能可靠地缩小它。** 在测量的运行中，加组合测试帮了一个任务，让另一个显著*更糟*。循环内更多的信号是更多可优化的表面。
- **故意作弊只是失败的一小部分。** 主导失败是*特性隔离*：各自正确却从不组合的组件。单元测试按定义隔离地测特性，所以它们测的东西恰恰是没坏的那个。
- **搜索过程会为假解决方案丢掉真解决方案。** 在一个有记录的案例里，agent 产出了一个真正能用的实现*和*一个小得多、背下了期望输出的实现。背答案的版本在唯一被测量的信号上得分更高，所以搜索保留了它，扔掉了真的。

结论不是"测试是坏的"。所有检查都值得建。结论是**台阶式变化是独立性，不是数量。**

## 阶梯

七级，最便宜的在最下面。自下而上建；它们组合。

| # | 级 | 它证明什么 |
|---|---|---|
| 7 | **确定性门** | 绿，或者没有合并。代码，永远不是提示词。 |
| 6 | **留出集场景** | 工作之前写的，从不给构建者看 |
| 5 | **视觉/截图评判** *（未搭脚手架——你自己建）* | 它在屏幕上真的看起来对 |
| 4 | **作为真实用户的 E2E** | 真实浏览器或真实客户端、真实数据、完整路径 |
| | **↑↑↑ 独立线 ↑↑↑** | *线以上，agent 看不到也编辑不了* |
| 3 | **集成** | 各块能一起工作 |
| 2 | **单元** | 它刚写的函数行为正常 |
| 1 | **静态** | 类型、lint、编译器 |

### 可达性约束，而且它是一个架构决定

**装置恰好以三种方式触达软件**：`http`（一个服务器）、`cli`（一个命令）、`library`（被导入和调用）。见 `templates/harness/appproc.py`。

一个渲染的窗口、一个游戏循环、一个 canvas、一个原生 UI **三者都不是**。所以这不是关于整洁架构的偏好，是一个前置条件：**规则必须活在一个无头、可脚本化的表面后面，让 E2E 能驱动。** 模拟与渲染分开，领域与视图分开。如果逻辑只存在于引擎节点和渲染循环里，就没有东西可断言，工厂无法在 3 级运行——不是因为技能受限，而是因为没有任何东西能检查工作。

在**绿地**构建上，在任何代码存在之前说出这个。那时它几乎免费，之后就是重写。在棕地构建上，它是第一件要查明的事，因为答案决定组件 5 是增量还是重构。

**`templates/harness/ci.py` 实现了 1、2、4、6 和 7。第 5 级没有脚手架**，说出来很重要：一份列出了脚手架不带的级的文档读起来像"你有这个"。你没有。`e2e.py` 捕获的截图是没人看的产物，直到有东西被写出来看它们。如果产品有一个值得评判的屏幕，就建第 5 级，把上面那行当作要做的事而不是已拥有的东西。要花多少钱见 `templates/harness/README.md` 的前端部分。

### 独立线

在集成之后画它。

**线以下的一切都在 agent 的优化循环内。** agent 能读那些检查、运行它们、对着它们迭代。给它足够多的尝试，它会满足它们——这正是你要求的，也正是通过它们证明得比感觉上少的原因。

**线以上的一切由 agent 看不到也编辑不了的东西写和跑。** 那是让其中任何东西成为证据的唯一属性。

阶梯的高度不是论证。线才是。agent 够得着三级、够不着四级，那个差距是自动合并唯一诚实的理由。

## 留出集

机制，作为一条要结构性强制执行的单一规则陈述：

> **验证者永远看不到代码是怎么写的。只看到要求了什么，以及代码现在做什么。**

### 验证者被给到什么

- 原始 issue，完全按提交时的样子
- diff
- 它自己运行的检查的输出
- 治理文件，**从基础分支取，永远不从 PR 取**

### 验证者绝不能被给到什么

- 实现计划，或构建者产生的任何设计笔记
- 构建者的推理、草稿笔记、或超出朴素标题的提交理由
- 构建者之前写的评论
- 产生代码的那次运行的任何产物

### 分层强制它

一条说"不要读计划"的提示不是强制。改成堆叠这些：

1. **独立进程、独立上下文。** 验证者作为自己的 job 运行，有自己的工作目录。它看不到兄弟产物，因为它们不在那里。
2. **窄取。** 拉 PR 数据时只请求需要的字段。在取层排除评论和评审，意味着任何闲聊即使意外也到不了评审者。
3. **先从基础分支读治理。** 在检出 PR *之前*从 `origin/main` 取 `MISSION`、`FACTORY_RULES` 和约定文件。PR 不能削弱它即将被评判所依据的规则书。任何碰到治理文件的 diff 都是自动拒绝，在任何其他评估之前评估。
4. **按节点限制工具。** 一个只读 diff 的评审者根本不需要文件系统访问。一个驱动浏览器的评审者只需要 shell 别的都不需要，并且应被显式禁止读源码。
5. **加一道绊网。** 让验证者在工作目录出现被禁产物时大声失败。它应该不可能；无论如何让它吵闹。

### 留出集场景住哪里

按强度递增：

| 位置 | 强度 | 代价 |
|---|---|---|
| 构建者工具配置从上下文排除的目录 | 弱——改一次配置就没了 | 免费 |
| 验证者检出而构建者从不检出的兄弟仓库 | 强 | 要维护的第二个仓库 |
| 版本控制之外，只在 runner 上 | 最强 | 它们不可见，所以悄悄腐烂 |

选用户真正会维护的最强的那个。没人更新的留出集会停止覆盖新行为，而且从不宣布它停止了。

**在工作之前写它们，不要在工作之后。** 见过实现之后写的场景是对实现的描述。

## 结构门 vs 提示词门

**提示词门**是提示词里的一条指令：*"只有所有检查都通过才批准。"* 模型可以被说服脱离它、可以误读证据、可以把跳过的检查算成通过的。

**结构门**是代码：bash、一个脚本、一个 CI 必需检查。它没有意见。

对用户诚实说出他们设计中的比例。实际上，真实工厂里几乎每个门最终都是提示词的，那可以存活——**只要真正重要的少数几个是代码。**

### 必须走代码的两个

1. **合并本身。** 跑 `gh pr merge` 的必须是一个读裁决文件并按它分支的脚本，而不是一个决定合并的模型。
2. **应用跑过的证明。** 一个应用真的启动了、E2E 真的执行了的正向断言。这是抓住下面最坏失败模式的那个。

任何坏结果不可恢复的其他东西都应该加入它们。

## 空不是通过

整个文档里最贵的一课，而避免它不花任何东西。

一个从没跑过的检查返回零失败。问"有东西失败了吗？"的代码把它读成成功。一个缺失的环境变量、一个崩溃的进程、一个超时、路径里的一个错别字——全都产生一个安静、自信的通过，而下游的合成器把一个**跳过**的检查算成**通过**的检查。

失败不是假设性的：这个模式曾经只靠静态分析就自动合并了 PR，同时相信一个完整的端到端套件已经跑过。

**修复无聊且彻底：断言正向标记。**

每个检查在成功时发出一个显式标记。门 grep 标记的*存在*，从不 grep "error" 这个词的*缺席*。

```bash
# in the check
echo "APP_STARTED backend=$BACKEND_PORT frontend=$FRONTEND_PORT"
...
echo "E2E_PASSED steps=7"

# in the gate - positive assertion, and a count, not a vibe
grep -q "APP_STARTED" "$LOG" || fail "app never started"
grep -q "E2E_PASSED" "$LOG"  || fail "e2e never ran"
STEPS=$(grep -oP 'E2E_PASSED steps=\K[0-9]+' "$LOG" || echo 0)
[ "$STEPS" -ge 7 ] || fail "e2e ran only $STEPS of 7 steps"
```

然后加兜底：**如果模型产出的裁决说批准但标记缺席，覆盖为拒绝并升级。** 读原始输出的确定性 bash 每次都胜过模型对那个输出的总结。假设总结者偶尔会无视它自己的规则，因为它会。

### 工厂对人类的输出也是输出，输出也需要断言

上面一切都是关于检查的。工厂还生产**给人看的产物**：解释拒绝的评论、PR 正文、升级通知。那些没人评分，而且它们静默失败。

在一次真实运行中观察到。Triage 完美地拒绝了一个范围外的 issue：裁决正确、标签正确、issue 以 not-planned 关闭、有一条按编号引用两条规则并给提交者留下申诉路径的书面拒绝。实际到达提交者的是两个字符：

```
@-
```

推理是在一个 shell 管道里拼的，而不是走工厂自己的评论助手，在 Windows 上管道塌缩成一个字面 `@-`。每个状态转换都是对的。`gh` 调用退出 0。运行报告成功。唯一丢失的是整个解释——那是人类永远会读的部分。

两条规则从中出来，第二条是通用的：

- **每个面向人类的写入都路由通过一个助手，并让助手成为唯一方式。** 节点里手写的 `gh issue comment` 和手写的合并是同一类错误：它在引号、编码或换行吃掉它之前都能用。
- **写完之后断言产物，而不是之前。** 把评论读回来，检查它包含你本来要发的规则引用。发布它的工具 `exit 0` 证明 API 调用成功了，不证明它带了任何东西。这正是空不是通过，应用到输出而不是检查上，而且很容易漏掉，因为输出感觉像副作用而不是结果。

这类 bug 存在的标志：**一个步骤的成功由它引起的转换来衡量，而不是由它生产的东西来衡量。**

### Slack 也不是通过

统计检查给你一个下限，而下限引出明显的下一个问题：什么阻止下限被降低？通常的答案是**棘轮**——一个持有每个检查族最小数量的锁文件，门断言 *observed >= floor*，第二个检查断言 *floor(head) >= floor(base)*。两半都需要。没有第二半，做法就是在同一个 commit 里删断言并降低数字。

那是正确的模式，而它有一个容易漏掉的失败模式。

**下限受保护，所以只有人类能提高它。装置改进得比人类提高得快。observed 和 floor 之间的差距恰好是门还绿时可以删除的断言数。**

在一个用这个技能建的真实工厂上测量。七个断言可以移除，而每个门仍然报告 `OK`。没有东西坏了，也没有人粗心：工厂一直在正确地加检查，而把下限提到匹配是一次它不被允许做的受保护编辑。

**然后同一个工厂在一轮装置工作之后又被测量了一次**，这是关键的部分：

```
metric               floor  observed  slack      floor  observed  slack
                       ---- before ----            ---- after -----
playthrough_checks       9        12      3          9        12      3
unit_tests               7         9      2          7         9      2
feel_checks             23        24      1         23        24      1
legibility_frames        -         -      -         60        87     27
                              TOTAL       7                  TOTAL   33
```

**漏洞在一轮里从 7 长到 33**，而且它增长*是因为装置变好了*。一个新检查族带着 87 帧对 60 的下限到达，那个盈余的每条断言都是可删的。改进扩大差距，这和棘轮该做的正好相反。

**所以让 slack 失败，或让它阻塞。** 选一个：

- **紧下限。** `observed != floor` 使门失败，把提升逼进接受新断言的同一次人类提交里。最严格，而且它让加一个检查暂时烦人，那是它有意义的代价。
- **Slack 阻塞拨盘。** 允许任何 slack 但把自主权钉在当前水平，直到下限被提升。更软，它把压力留在重要的地方。

你绝不能做的是把 slack 打印成一条注释然后继续。注释被那个已经知道的人读一次，之后漏洞随每次改进扩大。

## 设计 E2E 路径

一条路径，最有价值的那条，按用户使用它的方式演练。不是一个套件。

1. 在动态端口上启动应用，让并行运行不冲突。等健康检查。**它没起来就硬失败**——不要降级到"不可测"。
2. 用真实客户端驱动它。Web 应用用浏览器自动化 CLI；CLI 用真正的二进制；API 用真实 HTTP 客户端。
3. 断言用户会注意到的东西：渲染的输出，而不是 200 状态。
4. 每一步捕获截图或转录，并保留为产物。这是你决定是否信任循环时读的东西。
5. 总是清理启动的东西，包括失败时。

验证运行用专用数据库和专用凭据。对生产数据跑 E2E 是一起等待慢下午的数据丢失事故。

## 成本，诚实陈述

同一任务上已发表的受控对比：一个独行 agent 大约二十分钟产出非功能性结果，花个位数美元；一个 planner/generator/evaluator 装置——evaluator 用真实浏览器自动化驱动实时页面——大约六小时产出可用结果，花费大约二十倍。

二十倍的成本，换来唯一能用的版本。

那个比例是组件 5 的真实价格，用户应该在构建之前听到它，而不是在第一张发票之后。正如一位实践者所说：*任务验证者必须近乎完美，否则 agent 会解决错的问题。*

## 每次模型升级要删什么

装置组件不是永久的。其中一些的存在只是为了撑起模型后来已经长过的一个弱点，而且它们永远继续花 token 和注意力。

**每次模型升级，删一个装置组件并重跑你的评估。**

- 如果分数保持，那个组件是脚手架。让它保持删除。
- 如果分数下降，你找到了持久的东西。

反复出现的模式：**分解脚手架腐烂，验证存活。** 一个说"现在想想架构"的节点是会腐烂的资产——更好的模型不用提示就会那么做。一个说"在隔离的 worktree 里跑这个，以测试通过为门"的节点是持久的，因为它约束而不是指示。对抗性评估尤其倾向于值得保留，因为 agent 倾向于夸奖质量明显平庸的工作。

## 启用自动合并前的检查清单

在每一行都为真之前，不要把拨盘升到 3 级。

- [ ] E2E 路径能跑，而且被故意弄坏时会失败。**通过故意弄坏它来测试。** 一个从没失败过的 E2E 不被认为能用。
- [ ] 应用启动标记存在，门正向断言它。
- [ ] 合并由读裁决文件的脚本执行，不是由模型。
- [ ] 治理文件从基础分支取，碰它们在任何其他评估之前自动拒绝。
- [ ] 验证者的输入不包含计划、笔记或构建者评论。
- [ ] 留出集场景存在、住在构建者读不到的地方、而且是工作之前写的。
- [ ] 跳过的检查可证明地与通过的检查区分，而且如果裁决与原始标记不一致有确定性覆盖。
- [ ] 有停止按钮，而且它被故意用过一次。
