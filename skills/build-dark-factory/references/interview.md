# 访谈

**三个问题决定项目。另外六个只有用户能回答。其余一切都是他们要确认的默认值。**

这就是整个形状，而且是有意为之。这个文件的第一版按组件顺序问了 28 个开放问题，它以特定方式失败了：它以"你愿意为每个 issue 花多少钱"开场——一个它自己的笔记都承认几乎没人答得上来的问题——而且它开放地询问模板已经给出正确答案的东西。让人发明受保护路径清单、轮询间隔和留出集目录，教给他们的是"访谈是作业而不是对话"，而那些真正决定构建的问题出现在十几问之后，那时房间已经失去了。

**提出默认值不是捷径，是更好的问题。**"我要保护这五条路径，加上你的 CI 配置——还有别的吗？"得到的答案比"哪些文件是 agent 绝不能碰的？"更有用，只要十秒，而且没建过这东西的人也不会答错。

> **问任何问题之前先读 PRD，永远不要问它已经回答过的东西。** 把它的范围和反向目标作为提案播回去——*"所以 triage 接受这四个领域的工作，拒绝这六种，对吗？"*——把时间花在它留下空白的地方。让人重打一份他们已经写过的文档，是精心设计的访谈失败的最常见方式。

**每个问题都走问题工具。** Claude Code 里的 `AskUserQuestion`，或其他地方的等价物。不是大多数问题，不是那些有明显选项的——每一个，包括开放式的。这是硬性要求，没有例外。

这个文件的早期版本把问题分成选择器和散文，并论证这个拆分是承重的：为*"描述用户做的最有价值的一件事"*提供选项，会用你的猜测菜单取代你需要的答案。那个论证错了，而且错在一个机械原因上：

> **问题工具总是带一个自由文本的 "Other" 逃生口。** 所以一个开放问题经由它提问不会损失任何东西。想用自己的话回答的用户仍然可以，一次击键。本来会扫一眼段落然后回答*"你定吧"*的用户，现在看到三个具体候选，然后纠正最接近正确的那一个——那正是你想要的、原本得不到的答案。

那个旧论证里真实的东西作为对选项的约束幸存下来，而不是对工具的约束：对开放问题，选项必须**从他们自己的 PRD 和他们自己的仓库里起草，并引用来源**，绝不能凭空发明。从他们的材料起草的选项是他们的答案的回放，他们会乐意覆盖它。发明的选项把他们锚定到你的猜测上。如果你没有东西可以派生出选项，就在问题文本里说明，并依靠 Other。

**一次调用的形状：**

- 两到四个选项，一个标 `(Recommended)` 并放在第一位。
- 每个 `description` 一行：它意味着什么，或者他们选了它会发生什么。
- `header` 不超过 12 个字符。
- 把相关问题批量进一次调用——工具最多收四个——但绝不批量 Round 1 的三个问题，它们一次一个、按顺序问。
- 永远不要问 PRD 已经回答的问题。把它作为提案播回去。

**想要一个 LIST 的问题**——R2.1 要五样东西，R2.2 要一组不变量——是 **multi-select**，选项从他们 PRD 的反向目标起草，加上 Other 装你漏掉的。四个他们可以勾选的起草候选，是比空行好得多的第五个的提示，而被他们*取消勾选*的和他们保留的一样有信息量。如果第一遍产出的少于你的预期，用他们添加的东西再问一次。

## 适用于下面每个问题的两条规则

### 1. 总是带着推荐。每个问题，无一例外。

**永远不要递给别人一张白纸。** 一个没有提议答案的问题是作业；同一个问题附上草稿是两秒的纠正。这是"完成的访谈"和"中途被抛弃的访谈"之间最大的区别。

恰好标一个选项 `(Recommended)` 并放第一位，理由写进它的 description，一行。

对开放问题，选项就是草稿。从他们的 PRD 和仓库派生，并在问题文本里引用来源，例如：*"从 PRD 的 §6 看，旅程是这样的：打开应用 → 缩短一个 URL → 点击短链接 → 落在原页面。"* 然后把它作为推荐选项给出，加一两个合理的替代，让 Other 装任何你没想到的。

在推荐会不诚实的地方——真正的抛硬币，或只有他们能知道的事——就说**那个**，而不是发明信心：*"我这里没有推荐依据；它取决于 X。"* 那仍然比沉默好。

### 2. 在他们回答之前，主动解释难的部分

这些问题里有几个用到的词汇，只有建过这种东西之后才显而易见。一个不想承认没听说过留出集的用户会猜，而猜出来的答案会变成一条无法执行的规则。

所以**主动提供解释，而不是等着被问**：加一个显式的*"先解释这个"*选项作为真实选择。它花一行，被选中的频率比你预期的要高。

需要它的术语，以及如何一口气说出每个：

| 术语 | 一口气 |
|---|---|
| **holdout（留出集）** | 写代码的 AI 不被允许读的测试，所以它不能调优自己的作品去通过它们。这是合并没人审过的代码唯一诚实的理由。 |
| **mutation set（变异集）** | 你故意以特定方式弄坏代码，检查测试有没有发现。它衡量的是你的*测试*，不是你的代码。在跑过它之前，你不知道你的测试到底能不能失败。 |
| **the independence line（独立线）** | AI 能看到的检查与它不能看到的检查之间的分界线。线以下的一切都在它的优化循环内；给它足够多次尝试，它满足的是那些而不是你真正想要的东西。 |
| **the ratchet（棘轮）** | 必须运行的检查数量下限，保存在一个 AI 不允许编辑的文件里。它阻止质量被一次删掉一条断言地悄悄换走。 |
| **a structural gate（结构门）** | 由代码而不是由模型总结自己工作做出的合并决定。其中两个必须是代码，否则"我看着没问题"就是整个门。 |
| **the autonomy dial（自主拨盘）** | 多少事不需要你运行，0 到 5。3 级是关键的那个：代码合并而不需要人类读它。 |
| **E2E / the happy path（端到端 / 主路径）** | 一次穿过你软件的旅程，像真实用户那样走，端到端断言。不是每个函数一个测试——是一个人做的最有价值的那件事。 |
| **`APP_STARTED` / 正在运行的证明** | 你的软件真正起来时说出的一件具体的事——一个返回已知词语的页面，一个打印版本号的命令。没有它，启动时崩溃的软件和好好的软件在检查看来一模一样，而"没法测试"会被算成"没有问题"。 |

**`APP_STARTED` 在这个清单上，因为一次真实运行显示它被橡皮图章式盖章了。** 用户说*"行，就按你说的，已知地址已知响应，没问题"*——而它是仅有的两个必须是代码的门之一。它对任何运行过服务的人来说听起来显而易见，对没运行过的人来说毫无意义。在问 R2.3 之前解释它，不要等之后。

用户不技术时用那些大白话，技术时用精确的。不要讲课：一口气，然后问题，然后提供更多。

**在继续之前，把每个答案反射回一个具体产物**——"所以合并门是：PR 只有当 `APP_STARTED` 和 `E2E_PASSED` 都出现在运行输出里才合并。"访谈的意义是把意见变成可以写下来、可以运行的东西。

**对模糊的答案推回去。** 模糊的答案会变成无法执行的规则，而无法执行的规则比没有更糟：它读起来像保证。

### 3. 说出终点线在哪里，并在第八题左右再说一次

注意力在问题用完之前就用完了。一次真实运行中，用户在 R2.4 之后立刻问*"还有多久？我很想看到屏幕上有点东西"*——十二题中的第八题，而且离 R2.5b 只有两题，而 R2.5b 正是产出变异集、你最不想让一个已经停止思考的人回答的那题。

奏效的补救是**一条有名有姓的终点线加上对交付物的承诺**：

> "还有两个真正的问题，然后一个你扫一眼点过去的清单。然后我们就建。而且我会在写任何东西之前，准确说出屏幕上的第一样东西会是什么。"

不是"还有几个"。一个他们握得住的数字。开始 Round 2 时说它，感觉到漂移时再说一次——一个已经脱离却还在继续打字的人，比一个说自己无聊的人更糟，因为答案继续到来，而它们不再是真的。

## Round 1 —— 决定项目的三个问题

先问这三个，一次一个，在任何组件讨论之前。如果有人在三个问题之后走开，这三个就是你需要的。

> **在绿地仓库上，R1.1 是关于骨架（SKELETON），不是关于产品。** 按写出来的样子要旅程，因为它定义了产品是干什么的——然后说出你要先建它的哪个单片版本，以及它里面的其他一切都是 issue 一、二、三。见 Phase 0c。搞错这个是标准的绿地失败：agent 亲手建 MVP 好让装置有东西可测，工厂继承剩下的。

### R1.1 - "带我走一遍某人对这个东西做的最有用的一件事，从第一次点击到他们最终看到的东西。"

*那个*问题。答案成为工厂每次变更都检查的主路径。

逼它具体。不是"用户可以搜索"，而是：*打开应用 → 登录 → 输入一个带已知答案的查询 → 响应流式返回 → 显示一个引用 → 点击它 → 一个窗口在正确位置打开。*

**先从他们的 PRD 起草。** MVP 章节通常已经是这个的大部分。把它作为推荐选项提供，问它哪里不对。

**坏答案：** 任何你没法在屏幕上指出一点的东西。如果你看不见它，就没有东西能检查它，而 agent 会告诉你它工作正常。

### R1.2 - "你今天是怎么用 AI 构建功能的？"

让它说很久，**不要审讯**。一个带草稿答案的开放问题，不是关于规划、实现、评审、工具和框架的五部分问卷。收下他们给的，然后去看：`CLAUDE.md`、`AGENTS.md`、`.claude/`、`.cursor/` 通常已经在仓库里了，不用问就能回答工具那一半。

然后直白地说一次：*你刚才描述的每一步都会变成工厂运行的一步，唯一的区别是它们之间没有人点批准。*

一个追问，因为它比其余的加起来都值钱：**"那些步骤里你真正会读哪些，哪些只是点批准？"** 被橡皮图章盖章的是免费的自主权。他们真正读的那些才是检查必须做好的地方。

**如果他们没有流程**——*"我描述东西，粘贴进去，运行，把错误粘贴回去"*——那是真实答案，而且正是要被自动化的那个。不要深挖。说：

> "那就是流程，我们正在自动化它。唯一的区别是现在检查是你看结果——所以接下来几个问题是在建比那个看更好的检查，因为那个看会消失。"

然后把自带的提示词作为起点，并说明这一点。

### R1.3 - "你愿意让代码在没人先读的情况下到达你的用户吗？"

就那么问，然后展示拨盘。**3 级是推荐——说出来。** 人们常说 5；5 意味着工厂从任务书自己写工作，那是一个完全不同的决定。

期待一段停顿。那个停顿就是整个构建浓缩成一个问题，Round 2 里的一切都是为了让答案变成"是"。

然后校准一切的那个追问：**"如果一个坏变更真的混过去了，最坏会发生什么？"** 一个副业项目、一个内部工具、还是真实用户和真实金钱。那决定检查里有多少必须是代码而不是指令。

一个深思熟虑的"不"没问题——2 级是合法的。写进 `FACTORY.md` 里什么必须为真才能走更远，让它保持为一个决定，而不是一个再没人碰的拨盘。

## Round 2 —— 只有他们能回答的

**七个问题，每一个都是关于已经发生在他们身上的事。**

这就是这一轮建立其上的规则，而且它是一次修正。早期版本让人*设计*东西：说出功能组合时成立的三个属性，列出软件可能悄悄出错的方式，定义论证下必须保持为真的东西。那些是对的产物，却是错的问题——它们是把一个设计练习递给一个来这里回答自己产品问题的人。写这个技能的人迷失在他自己的访谈里。

**所以：问他们的经验，你自己派生产物。** 一个用户应该能在从没听说过这个技能的情况下，凭记忆、关于他们熟悉的软件，回答下面的每个问题。把那些答案变成场景、缺陷集和规则是你的工作，而且你默默做。

### 多假设一些。这就是交易，而且是有意的。

**当一个问题难以简单地问出来，你自己回答它，然后请他们纠正。** 你有他们的 PRD 和他们的仓库，这绰绰有余，足以起草这里几乎所有东西的像样的第一版。一个他们一键就能拒绝的草稿答案，比一个他们放弃的完美问题值钱。

具体来说，按这个顺序：

1. **从他们的材料起草。** 他们的反向目标已经是绝不做清单的大部分。他们的 MVP 已经是主路径的大部分。他们的代码命名了会坏的东西。
2. **把它作为推荐选项提供。** 两三个替代，然后 Other。
3. **只要求纠正。** *"这些哪个是错的，我漏了什么？"*
4. **你不得不猜的地方，用一行说出来**——并把它作为假设写进 `MISSION.md`，让它之后可见，而不是默默承重。

**牺牲是真实的，而且被接受了。** 假设意味着有时假设错，而用户纠正错误草稿，好过同一个用户盯着空白问题回答*"我不知道，你定吧"*——那是旧访谈真正产出的答案，而且它不携带任何信息。错误的猜测会被纠正。被放弃的问题不会。

**你绝不能假设的：** Round 1 里的任何东西，以及任何决定什么算通过的东西。猜他们是否接受无人审阅的合并，或检查必须多严格，不是简化——是替他们决定项目。

**问题里永远不要说这些词：** holdout、mutation set、invariant、ratchet、independence line、structural gate、composition、marker、E2E。每一个命名了一个用户没有理由知道的解决方案。如果一个术语必须出现，它出现在答案*之后*，一句话，解释你在用他们刚说的东西做什么。

### R2.1 - "这些里哪些是它绝不该做的——不是现在不做，是十年内都不做？"

**从 PRD 的反向目标起草选项**，它们通常已经是清单的大部分，做成 multi-select。他们取消勾选的和他们保留的一样重要。

**要抓住的区别：PRD 说"现在不做"，工厂需要"永远不做"。** 逐个走反向目标并分类。"现在不做"的进 backlog，**绝不能**列为范围外，否则轮到它们的时候工厂会拒绝那些工作。

然后一个带 Other 的开放追问：*"还有别的吗——即使很容易也应该拒绝的？"* 他们卡住时只用类别提示——新数据源、支付、移动、社交、公开 API、集成。

**它会变成什么：** `MISSION.md` 里的范围外清单，它让工厂能在凌晨三点拒绝一个貌似合理的请求。

### R2.2 - "什么会让你放下手里的一切立刻修它？"

"什么必须永远成立"的大白话版本。人们立刻回答，因为它是一种他们经历过的感觉：寻呼机，那个你不会拖到周一的事。

从 PRD 起草三条让他们纠正：*"我会猜——用户数据泄漏到另一个账户、限流失效、任何人能看别人的记录。哪些是错的，我漏了什么？"*

**它会变成什么：** `MISSION.md` 和 `FACTORY_RULES.md` 里的属性，任何请求都不允许争辩掉。与 R2.1 不同：那些是你不会加的功能，这些是你*加*的任何东西都改变不了的属性。

### R2.3 - "你做完一个变更之后，实际上会做什么来检查你没弄坏东西？"

他们说什么都是规格，包括*"我到处点几分钟"*——**尤其**是那个。让点击过程被叙述出来，一步一步，因为那是必须被自动化的检查。

**坏答案：** *"我跑测试。"* 问他们在测试通过之后、相信它之前做什么。

### R2.3b - "如果你没在看屏幕，你怎么知道它运行正常——不只是启动了？"

两个必须是代码的东西之一。一个会响应的 URL、一个渲染出来的页面、日志里的一行。一个启动、挂住、返回零的进程，看起来和一个健康的完全一样。

**坏答案：** *"它能启动。"*

### R2.4 - "让测试通过而不真正修任何东西的最懒的办法是什么？"

就用这些词问。这是关于他们的代码的问题，不是关于 agent 的，人们答得很好还很享受：删测试、弱化检查、mock 被测的东西、抓住错误继续走、特判测试输入。

**它会变成什么：** `FACTORY_RULES.md` 里的规则，以及在能做到的地方变成代码里的检查。

### R2.5a - "给我讲一个绕过你的测试还是到了你面前的 bug。发生了什么？"

**这取代了旧访谈里最难的问题**，那个问题让人说出三个只在功能一起用时才成立的属性。几乎没人能凭空做到；文件自己承认了，然后还是问了。

每个人都有这个故事，而故事就是同一个产物。一个活过测试套件的 bug 几乎总是需要两件事同时为真的那种——它保存了但没重载，它第一次行第二次不行，第二个用户看到了第一个用户的数据。那正是需要的材料，而且它作为记忆到达，而不是作为设计练习。

要两三个。然后一个追问：**"什么能抓住它？"**

**它会变成什么：** 场景保存在构建 agent 读不到的地方，这是合并没人审过的代码唯一诚实的理由。在*他们回答之后*用一句话说那个，不要在前面说。

**如果他们真的一个都没有**——没有历史的绿地项目——从 PRD 起草，配对必须互相存续的能力，问哪个是错的：*"做一个，重启它，它还在吗"*、*"做两次，中间夹点别的，答案一样"*、*"你拒绝过的东西不会悄悄变成接受的。"*

### R2.5b - "如果我悄悄弄坏一件东西而没人注意到，什么最疼？"

整个访谈里最好的问题。保留这些词。

**但别再要六个了。** 旧版想要六七个，人们卡住，说回头再补，然后永远没补。要**那个最吓到他们的**，然后从它和他们的代码起草五个，问哪些是错的。编辑清单很容易；从无到有造一个清单是访谈死掉的地方。

要起草的形状，用他们真实的功能命名而不是抽象地说：一个悄悄反过来的检查、一个停止跳动的计数器、一个永远是同一个数的答案、一个返回而不是抛出的错误、一次不再发生的保存所以一切都好直到重启、一个边界上的 off-by-one。

**它会变成什么：** 检查被衡量的那些故意缺陷。之后值得说的一句话：*这些里每一个混过去的，都是一种现在能在没人读 diff 的情况下上线的 bug。*

### R2.7 - "上线之后，你会跑什么或点什么来证明它真的在工作？"

以及：**它工作的话你会看到什么？** 两半都要，因为一个没有检查的部署步骤是一个无法失败的步骤，而无法失败的步骤是一句评论。

逼一个用户会注意到的东西——一个被服务的请求、一个渲染的页面、一行写入的记录。

---

**以前在这里的三个问题现在搭 Round 3 的车**，作为要修改的默认值而不是要回答的问题。它们是访谈里最抽象的，而且三个都有已经写下来的正确答案：

| 以前 | 现在 |
|---|---|
| *"这台机器永远检查不了哪些部分？"* | 从 PRD 起草——感觉、外观、可读性——在 Round 3 调用里确认 |
| *"工厂可以自己决定什么，必须停下来问什么？"* | 拆分是固定政策，所以只问新增的部分，在 Round 3 |
| *"什么绝不能合并，什么你宁愿上线也不愿卡住？"* | 推荐无聊的默认：它必须能启动，主路径必须通过，没碰受保护文件 |

*（没有推还是轮询的问题。答案永远是轮询：一个坏掉的推送触发器会静默失败，看起来和一个无事可做的工厂一模一样，而且 GitHub 根本不会对默认 token 的 commit 触发工作流。告诉他们；不要问。见 `deployment.md`。）*

---

## Round 3 —— 默认值，一次调用确认完

**把这些作为一份填好提议值的单一清单发出去，问要改什么。** 不要一次一个，也不要以问题的形式。每一行都有一个能用的默认值，大多数用户会改一两个。

**这一轮就是为问题工具而生的。** 一次调用，**multi-select**，措辞是*"这些里你想改哪些？"*，提议值写在每个选项的 description 里。什么都不选是有效且常见的答案，而且只要一击而不是十条回复。只为选中的那些要新值。

小心选项上限：真实的问题工具一次调用只允许几个选项。把用户最可能想改的放前面——并发、轮询间隔、PR 上限、受保护路径——其余作为纯文本放在旁边。不要为了塞进组件而丢行。

| 什么 | 提议的默认值 | 为什么它是默认值而不是问题 |
|---|---|---|
| **受保护路径** | 治理文件、`factory/**`、`.factory/locks/**`、`.factory/holdout/**`、`.github/`、`deploy/`、`infra/`、Dockerfile、认证和限流模块、lockfile | 播种它，然后问还有什么。他们的答案是追加，不是清单 |
| **绝不提交的文件** | `.env*`、`*credential*`、`*secret*`、`*.pem`、密钥、服务账号 | 与"绝不编辑"是**不同的问题**：无法编辑文件不能阻止 `git add -A` 发布一个下个月出现的文件。变成 `FACTORY_SECRET_FILES`，pre-flight **拒绝启动**直到每个都被 git 忽略 |
| **隐藏场景住在哪里** | `.factory/holdout/`，按节点封锁读取并在 diff 上守护 | 一个正确答案，已经出厂。提更强的选项——兄弟仓库、或 runner 上版本控制之外——取他们真正会维护的最强的那个。没人更新的留出集比没有更糟 |
| **PR 大小上限** | 500 行，12 个文件 | 粗但有用。无人监督的 agent 会交 3,000 行的 PR，而"没人能审"是工厂连原则上都不可审计的地方 |
| **轮询间隔** | 每 30 分钟 | 比感觉上该有的慢。快速循环在任何人注意到错误之前就把错误的花费放大 |
| **并发** | 一 | 并行是每目标竞争生存的地方。在串行版本无聊之后赢得它 |
| **停止按钮** | `.factory/STOP` kill 文件**和** `factory:stop` 标签 | 两个，因为它们在不同的地方失败。文件在网络断开时也能用 |
| **每节点失控守卫** | `FACTORY_MAX_BUDGET_USD` | 一个高到撞上它就意味着出事的顶。不是预算——是防永不终止节点的守卫 |
| **模型路由** | **规划**槽用高级，其他都用便宜的 | 高级模型放在 plan/implement 其中*一个*，买到放两个的大部分质量。零到一是一个大而真实的改进；一到二通常是噪声。选错槽很便宜；零个高级槽才是真正花钱的 |
| **约定文件** | 他们现有的 `CLAUDE.md` / `AGENTS.md`，保留 | 如果存在它就已经是答案。**拆分它，不要替换它**——把只属于工厂的规则移到 `FACTORY_RULES.md`。如果不存在，问他们会告诉新员工第一天的什么 |

有四件事必须**陈述而不是提议**，因为没有安全默认值：

- **哪个编码 agent 在将要运行它的机器上认证好了。** 不是哪个最好——是哪个今天就能用。工厂 shell 出去调一个无头命令并读退出码；每个 agent 都暴露那个。
- **工厂在哪里运行。** 笔记本、VPS、CI runner、容器。这决定凭据寿命、调度能否扛过重启、应用能否被启动来做 E2E、沙箱能触达什么。
- **工作怎么到来。** 通常是 GitHub issues；有时是一个带指向它的 issue 的规格文件。细节不如"恰好选一个，让一切从它读"重要。
- **什么触达他们，以及怎么触达。** 恰好一个升级通道，而且它应该安静——如果什么都通知，他们会静音它，然后什么都不通知。**要一个真实的命令，不是偏好**："Slack 吧，大概"经不起 runner 的接触。`FACTORY_NOTIFY_CMD` 需要一个能跑的东西。问他们周六不在机器旁时，十分钟内真正会看到什么。`setup.md` 每个都有能用的行。**坏答案：** *"我就去查一下文件。"* 没人查文件——这正是这个东西存在的全部理由。一个唯一输出是没人打开的文件工厂不是无人值守，是无人监控。

还有一个，直白地问：**"你怎么回滚？"** 如果答案是"我会向前修复"，没问题，但它必须被说出口——无人值守系统最终会合并坏东西，恢复路径不应该在凌晨 2 点被发明。

## 收尾访谈

在写任何文件之前，把整个东西作为一份规格回放：

- 构建它的 PRD，按路径，以及从它压出来的任务书
- 五件**永远**范围外的事，与"不是这个季度"分开排序
- 硬不变量和受保护清单
- **他们现有的流程，写成工作流要跑的有序步骤**
- E2E 主路径，叙述为步骤
- 两个结构门
- 隐藏场景住在哪里
- 选定的 agent，以及哪个模型坐在规划槽
- 它在哪里运行，什么调度它
- 合并时发生什么，**证明构建工作的命令和它打印的东西**，以及怎么回滚
- 目标自主级别，以及先建的那个级别
- 停止按钮，以及触达他们的那一个通道

**其中六个是工厂拒绝无它运行的设置**，所以模糊的答案不是软失败——是被堵住的第一圈。把它们点名回放：

| 答案 | 变成 | 没有它会怎样 |
|---|---|---|
| **什么绝不能合并** | 它必须能启动，主路径必须通过，没碰受保护文件——其他一切都能上线 | 无聊的答案对几乎每个项目都是对的，而且比空问题容易争辩得多。这以前是开放问的，产出过一个的清单或四十个的清单 |
| **什么只有人才能判断** | 从他们的 PRD 起草：感觉、外观、措辞、新人能不能看懂 | 工厂的范围比产品小，而且总是以同样的方式小。派生它、展示它、让他们加。写进 `MISSION.md` 作为永久人类，所以绿灯永远不被读成"产品很好" |
| **做什么之前应该问** | 回滚无法撤销的变更：schema 迁移、钱、认证和密钥、任何把东西送出大楼的 | 拆分本身是固定政策——它决定普通产品值并向你展示，它从不决定什么算通过——所以只有新增的部分值得要。只在一个方向上推长度的边界：清单上的每样东西都花吞吐，清单外缺的每样东西花的不止吞吐 |
| 绝不能提交的文件 | `FACTORY_SECRET_FILES` + `.gitignore` | pre-flight 拒绝；没有一圈会开始 |
| 证明应用运行的命令 | `FACTORY_VALIDATE_CMD` | 门没有东西可跑 |
| 它启动的可观测证明 | `FACTORY_REQUIRED_MARKERS` 里的 `APP_STARTED` | 门无法区分跳过的和通过的 |
| 健康命令及其输出 | `FACTORY_HEALTH_CMD` / `_MARKERS` | `deploy.sh` 拒绝发布 |
| 停止按钮 | `FACTORY_STOP_FILE` / `factory:stop` | 没有任何东西能停下它 |
| 升级通道 | `FACTORY_NOTIFY_CMD` | 无人值守悄悄地意味着无人监控 |

**还有四样东西是脚手架作为工作示例交给你的，只有在你替换它们之后才属于你。** `factory_doctor` 在每一样上卡住，直到你删掉它的标记，因为一个对别人的产品亮绿灯的门比没有门更糟：

| 来自 | 你写 | 产生它的答案 |
|---|---|---|
| `harness/e2e.py` | 被断言的旅程 | R1.1 |
| `.factory/holdout/run.py` | 构建者读不到的组合场景 | R2.5a |
| `harness/mutations/defects.json` | 必须被抓住的缺陷 | R2.5b |
| `factory/prompts/*.md` | 你的流程，去掉批准 | R1.2 |

如果还有任何一行模糊，那就是工厂会失败的那一行。回到它。
