# agent、编排器与调度器

三个本应分开的选择，人们常常把它们合并成一个。在访谈中明确分开它们，因为其中只有一个事后难以更换。

| 选择 | 它是什么 | 可替换程度 |
|---|---|---|
| **编码 agent** | 把提示词变成编辑的东西 | **非常容易。** 它是一个配置值。 |
| **编排器** | 定义并运行多步工作流的东西 | 难。这是真正的承诺。 |
| **调度器** | 决定任何东西何时运行的东西 | 容易，而且它必须保持无聊。 |

---

## 1. 编码 agent

每个无头编码 agent 都暴露几乎相同的契约：一个 print/exec 标志、一种结构化输出模式、一种跳过审批的方式、一个用于恢复的会话 id。工厂 shell 出去调一个命令并读退出码。这就是全部接口。

| Agent | 无头调用 | 值得知道的 |
|---|---|---|
| **Claude Code** | `claude -p "..." --output-format json` | `--allowedTools`、`--disallowedTools`、`--permission-mode`，以及作为单次调用硬性花费上限的 `--max-budget-usd`。**没有** `--max-turns`；见下面的警告。 |
| **Claude Agent SDK** | Python `claude-agent-sdk`、TS `@anthropic-ai/claude-agent-sdk` | 进程内而不是 shell 出去。想中途检查或插话时更好。 |
| **Codex** | `codex exec --sandbox workspace-write --ask-for-approval never` | 沙箱模式是要搞对的东西。 |
| **Cline** | `cline schedule create ... --cron "0 2 * * *"` | 自带**原生 cron**，所以部分调度器已经替你建好了。 |
| **Goose** | `goose run --instructions <file>` | 也有自己的 `goose schedule`。 |
| **Amp** | `amp -x "..."` | 想要事件驱动而不是轮询的话有 webhook。 |
| **Pi** | `pi --print` / JSON 模式 | 提供商无关；当重点是不要被锁定在一个模型厂商时有用。 |
| **Antigravity** | `agy -p "..." --output-format json` | 注意默认打印超时——它很短，会在真实工作中途杀掉它，看起来还像模型失败。 |

**在把精确的标志写进工作流之前，对照当前文档验证。** CLI 表面会移动，一个悄悄改变含义的标志比一个报错的更糟。这些 CLI 中有几个不会拒绝未知标志——值会落进提示词里——所以过时标志会变成隐形提示注入。

> **这一页自己就写错过，这是它为什么这么说的最好证明。**
> 它曾把 `--max-turns` 列为 Claude Code 的标志。它不是。Claude Code **接受它、忽略它、退出 0**——所以运行器在每个节点上都传了花费上限，所有评论都声称上限在生效，而实际上从未生效。没有任何报错，没有任何日志，它浮出水面唯一的原因是有人跑了 `claude --help`。
>
> **一个悄悄不生效的守卫比没有守卫更糟**，因为你不再盯着它守卫的东西。在信任你写进工作流的任何标志之前运行这个：
>
> ```bash
> for f in --allowedTools --disallowedTools --permission-mode --max-budget-usd; do
>   claude --help | grep -q -- "$f" && echo "OK $f" || echo "MISSING $f"
> done
> ```
>
> 而且无论如何，优先用**美元**上限而不是轮次上限。轮次是花费的代理指标，而且是个烂代理；`--max-budget-usd` 才是你真正关心的东西，而且它真的会强制执行——触发时运行会以 `is_error: true` 返回。

### 选择

选那个已经在将要运行工厂的机器上认证好的。不是最好的那个。是今天能用的那个。因为 agent 真的是可替换的，这个选择便宜且可逆，把它当大决定会把注意力花在组件 5 该花的地方。

### 什么不会移植

大声说出来，因为真正的时间都花在这里：

- **凭据过期**，静默地，运行中途
- **没人警告你的成本悬崖**
- **多数没有默认会话超时**
- **你要自己设计的沙箱出口**

每个 agent 都是同样的四个问题。没有一个替你解决。

## 2. 编排器

把"plan → implement → review → gate → merge"定义为带依赖的步骤的东西。真正的承诺；换它意味着重写每个工作流。

### 盒子里有一个

`templates/runner/` 是下面第一种编排器的工作版本——纯脚本、单机、完全透明——从一个真实运行的工厂里搬出来的。没有理由就别重写，直接复制：

| 文件 | 它是什么 |
|---|---|
| `factory/config.sh` | **你唯一要编辑的文件。** Agent、模型、验证命令、标记、拨盘、限制、路径 |
| `factory/orchestrator.sh` | 调度器：固定优先级、每目标锁、自主拨盘、停止按钮 |
| `factory/run-workflow.sh` | **运行器。这就是编排器** ——不存在管道的第二个定义 |
| `factory/gate.sh` | 结构门：必需标记、计数、校准、裁决 |
| `factory/guard.py` | 受保护路径和大小上限。**默认关闭**（fail closed） |
| `factory/merge.sh` | 合并。代码，永远不是模型 |
| `factory/deploy.sh` | 轮询、健康检查、切换、回滚 |
| `factory/state.py` + `gh_backend.py` | 转换表，以及作为状态的 GitHub 标签 |
| `factory/tripwire.py` · `cost.py` · `node_failure.py` | 留出集绊网、token 计量、节点为何失败 |
| `factory/prompts/*.md` | 七个节点。**访谈的输出——重写这些** |

**一个管道的两个定义多了一个。** 那个仓库曾有一段时间在 bash 之外还带着 YAML DAG 定义，理论是一个引擎会运行它们。没有任何东西运行，所以它们漂移了——它们漂移成了 `deny_paths` 的一条，让留出集读取封锁看起来被强制执行了，而真正强制执行它的只是提示词里的一句话。**一个发明安全属性的过期规格比没有规格更糟**，没人运行的那个总是漂移的那个。选一个定义。

如果你自带引擎，运行器仍然是*每个节点必须做什么*的参考：每节点新上下文、工具白名单、传给 agent 的留出集拒绝、一个显式提交步骤、从根检出运行的 guard、来自基础分支的治理。移植属性，不要移植 bash。

| 选项 | 形态 | 适合 | 代价 |
|---|---|---|---|
| **纯 shell 脚本** | 顺序调用、退出码 | 小工厂、单机、完全透明 | 无并行、无恢复，状态要自己发明 |
| **YAML DAG 运行器** | 声明的节点和边、每节点模型和工具限制、产物目录 | 你想要节点级的上下文隔离和工具控制——组件 5 需要这个 | 一个要运行和理解的依赖 |
| **GitHub Actions** | 仓库里的 job 和 step | 你想放进 CI 且不加额外基础设施 | 临时 runner 让长 E2E 和应用启动别扭；注意 `deployment.md` 里的 token 陷阱 |
| **进程内 agent SDK** | 你自己的程序驱动会话 | 你需要自定义控制流或中途插话 | 你现在在维护一个编排器 |
| **模型主导的编排** | 一个 agent 生成并协调其他 | 灵活，适应意外形态 | 非确定性；工作的形态每次由模型决定 |

### 真正的权衡，公平陈述

**声明式 DAG** 意味着你写好了节点和边，模型填充工作而不选择形态。可复现、可调试，而且它让你能按节点设置工具白名单和新上下文边界——这正是留出集被结构性强制执行而不是靠指令执行的方式。

**模型主导** 意味着一个协调 agent 决定如何分解和生成。更自适应，更不可预测，而且更难证明独立属性。

两者没有赢家。但注意组件 5 需要哪一个：**留出集是关于"给定步骤被允许读什么"的陈述**，当步骤是声明的时候比运行时发明的时候容易保证得多。

## 3. 调度器

> **调度器必须是整个系统里最蠢、最确定的东西。它是唯一一个"错答案比没答案更糟"的组件。**

### 不要问模型该跑什么

LLM 被问"有什么待办工作？"会为不存在的工作发明调度——为从未提过的 issue 跑 run、为不存在的 PR。那是一个听起来很合理但背后空无一物的答案，而工厂会据此行动。

用 bash。固定优先级顺序。无聊的共享状态。

### 共享状态

GitHub 标签就够了，而且它们有真实优势：可见、人类用手机就能编辑，而且它们*就是*审计轨迹。

```
factory:accepted → factory:in-progress → factory:needs-review
                                        ├── factory:approved      (合并，然后部署)
                                        ├── factory:needs-fix     (回到 in-progress)
                                        └── factory:needs-human   (停止；唯一能触达你的东西)
```

没有数据库。没有消息总线。如果信息要在工作流之间传递，它作为标签或评论移动。这个约束让系统保持可检查，而可检查是凌晨 2 点你想要的属性。

#### 标签不是的四件事，都是血泪教训

标签是好的共享状态，是糟糕的锁。下面每一条都是先被写成预测、然后被真实运行打脸的。

1. **没有 compare-and-swap。** 两个调度器都读到 `factory:accepted` 然后都认领这个 issue，因为"读标签、写标签"不是原子的，API 里没有任何东西让它原子。**搬到 GitHub 不会让你的每目标锁退休。** 如果你为文件后端建了一个，留着；标签是审计轨迹，不是互斥锁。
2. **标签写入对标签读取不是立即可见的。** 实测设置标签到在列表端点看到它之间有 2 到 4 秒延迟。写完立刻重读的调度器偶尔会看到旧世界。
3. **停止按钮必须是你*添加*的标签，读取必须默认关闭。**"移除标签以停止"是显而易见的設計，但它反了：缺失的标签无法与列出它失败的 API 调用区分，所以一次网络波动读起来像"继续"。添加 `factory:stop`，把*任何*列出它的错误当作已停止，并且保留一个本地 kill 文件，因为本地那个在网络断开时也能用。
4. **关闭不是一种处置。** `deferred` 和 `rejected` 都是已关闭 issue，没有标签就无法区分。搞错了，工厂就会在路线图到来的那个季度拒绝它——这正是任务文件的 deferred-vs-never 拆分要防止的失败。GitHub 还会执行你的表从未授权的转换：合并 PR 里的 `Closes #N` 会关闭 issue，所以"已关闭且无标签"是一个你必须处理的真实状态。

#### 分支保护不能替代你的合并脚本

GitHub 上诱人的做法是删掉 `merge.sh`，让必需检查加分支保护当门，理由是规则集不是 agent 能编辑的东西。

在关键情况下，它能。**工厂以管理仓库的主体身份认证，能编辑规则集的账户就能绕过规则集。** 除非你为工厂配置了单独的最小权限身份，并验证它不能管理仓库，否则合并必须留在你能控制的代码里。

同一区域还有两个小陷阱：如果你的门在调度机器上执行而不是在 Actions 里执行，不会发布任何 check run，所以一个*必需*检查从不报告会永远阻塞所有合并。还有，第三方 App 可以在 PR 打开几秒后就评论它，所以一个读 PR 评论的评审者读的是陌生人的文字。让它改从磁盘读 diff 和 issue。

### 优先级顺序，以及为什么它是承重的

1. **修复** 一个标着 needs-fix 的 PR（在尝试上限内）
2. **验证** 一个标着 needs-review 的 PR，最老的优先
3. **实现** 优先级最高的已接受 issue
4. **triage** 未 triage 的 issue

**先完成在途工作，再开始新工作。** 反过来，工厂永远在 triage，而自己的 PR 烂掉，吞吐看起来忙碌实际归零。

### 一个退出 0 却什么都没做的节点

真实调度中出现过三个不同版本，而同样的工作流由人手动驱动时它们都不可见。

- **一个 agent 撞上轮次上限**，升级了，消息点名了一个不存在的故障。昂贵的规划半场已经付了钱然后被扔掉。读 agent 自己的 JSON 结果，报告真正的终止原因。
- **一个 agent 被要求运行白名单不覆盖的命令**，被拒绝，用文字礼貌地说出来，然后退出 0 什么都没改。**工具拒绝不是失败也不是成功**；它是节点告诉你它想要一个得不到的东西。按节点记录拒绝，并且在 diff 空着回来时把它们引用进升级消息。做过一次这个就发现，一个规划节点从被写出来起几乎每次运行都在被静默拒绝工具——请求、被拒、绕过去。
- **一个节点编辑了它的 worktree 却没提交任何东西**，清理在 guard 正确报告两个变更文件几秒后删掉了 worktree。人类不用被告诉就会提交。agent 不会，除非工作流把它做成一步。

一般规则：**对产物断言，而不是对退出码断言。** 一个没有产出 commit、PR 或 diff 的运行没有成功，无论它返回什么。

### 不可选的限制

- **尝试上限。** 每个 PR 两次修复尝试，然后升级。没有它 PR 会来回弹直到预算耗尽。
- **并发上限，从 1 开始。** 只在串行版本无聊之后提高。提高时加每目标锁：绝不派发 (workflow, target) 对已在途的工作流，否则两个运行会在同一个 PR 上竞争。
- **批量上限。** 限制每次运行的 triage 数量。backlog 应该跨周期排空，而不是在一次昂贵的爆发中。
- **洪水保护**，如果其他人可以提 issue。限制每作者每天 issue 数；你自己豁免。
- **停止按钮。** 调度器检查的 kill 文件，或禁用调度。显而易见、有文档、故意测试过一次。

### 把每个编辑节点限定到它自己的 diff

任何编辑代码的节点都必须被拴在它允许碰的文件上：

```bash
git diff --name-only <base>...HEAD
```

一个没有 diff 范围的清理或重构节点会把六文件的 PR 长成十一文件，并在途中引入一个 bug。如果节点说不出它可以碰哪些文件，它会碰更多。

### 模型路由

两个槽决定质量：**规划**的那个和**实现**的那个。

把高级模型放进其中**一个**，买到放进**两个**的大部分质量。从零个高级槽到一个是大而真实的改进。从一个到两个通常在噪声以内。

**用贵的模型规划。用便宜的构建。** 选错槽很便宜。零个高级槽才是真正让你花钱的。

在相信它之前先在你自己的仓库上测量，测量时说明你的噪声底——没有噪声底的基准只是一个故事。
