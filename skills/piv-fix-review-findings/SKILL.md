# 修复评审发现

评审产出了发现——但评审是**输入，不是工单。** 你决定每条发现怎么办。

代码评审（文件或问题描述）：$review

方向/范围（现在修什么 vs 推迟什么）：$scope

如果 Code-review 是一个文件，**先完整阅读该文件**，这样你在分级前理解每条发现。

## 1. 先分级（人的决定）

在碰代码之前对发现排序。尊重 scope 参数中的任何方向；如果不清楚，把发现分组展示并**询问**，而不是默认全修：

- **现在修（这个 PR）** — 真实、在范围内、属于本次更改。
- **推迟 / 记为 issue** — 真实但以后；不要臃肿这个 PR。**创建 tracker issue**（或记录它）而不是在这里修。
- **需要人看 / 手动测试** — 任何你在信任之前应该亲手检查或测试的东西。标记它，不要静默自动修。
- **噪音 / 不修** — 说明为什么，然后丢弃。

不要被评审者替你决定范围——"真实，但以后"是有效且常见的判断；一个干净的小 PR 胜过一个大而全的。

## 2. 修复"现在修"集合——一次一个

对每个：
1. 解释哪里错了。
2. 做修复。
3. 创建并运行一个证明它的测试。

## 3. 验证

运行 `piv-validate` 技能来定稿修复。

## 4. 如果在 PR 上操作——提交并推送

如果这些修复在 PR 分支上，**提交它们（用 `piv-commit`）并推送**，让 PR 反映这些修复，评审可在更新后的 PR 上重新运行。如果什么都没修（全部推迟），就没有可推送的——只要确保推迟项被记录为 issues。

## 输出

一份简短报告：什么被**修复了**（带其测试）、什么被**推迟/记录**（带 issue 引用）、什么需要**手动查看/测试**——以及，如果在 PR 上，**推送的提交** + PR 已更新的确认。
