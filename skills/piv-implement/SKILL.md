# 执行：按计划实现

## 要执行的计划

读取计划文件：`$ARGUMENTS`

## 开始之前——在特性分支上工作

一个 ticket 在自己的分支上构建，这样它能成为一个 PR。**理想情况下你已经在那个分支上——在规划之前就切好——这样你做的计划提交就在该分支上，并随 PR 一起走；提交在 base 分支上的计划不会出现在这个分支的 PR 里。** 如果你还在 base 上，此步骤现在创建分支。检测 base 分支（不要硬编码 `main`）：`git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's@^refs/remotes/origin/@@'`（回退 `main`）。

- **在 base 分支上，工作树干净** → 创建一个：`git checkout -b feature/<plan-slug>`。
- **已经在特性分支或 worktree 上** → 直接使用它。
- **在 base 分支上但有未提交更改** → 停下：先提交或 stash。

（每个 ticket 一个分支也是后来并行 worktree 干净的前提。）

## 执行说明

### 1. 阅读并理解

- 仔细阅读整份计划
- 理解所有任务及其依赖
- 记下要运行的验证命令
- 审阅测试策略

### 2. 按顺序执行任务

对"逐步任务"中的每个任务：

#### a. 导航到任务
- 识别需要的文件和动作
- 如果修改现有文件，先阅读它们

#### b. 实现任务
- 完全遵循详细规格
- 与现有代码模式保持一致
- 包含适当的类型提示和文档
- 在合适的地方添加结构化日志

#### c. 边做边验证
- 每次文件更改后检查语法
- 确保导入正确
- 验证类型定义正确
- **在开始下一个任务之前，运行该任务自己的 `VALIDATE` 命令。** 计划中的每个任务都带一个。任务在检查通过之前不算完成——如果失败，当场修复，而不是把失败带到下一步。完整套件仍会在步骤 4 运行；这道每任务门禁是为了防止步骤 4 的问题堆积。

### 3. 实现测试策略

完成实现任务后：

- 创建计划中指定的所有测试文件
- 实现提到的所有测试用例
- 遵循概述的测试方法
- 确保测试覆盖边界情况

### 4. 运行验证命令

按顺序执行计划中的所有验证命令：

```bash
# 完全按计划中的指定运行每个命令
```

如果任何命令失败：
- 修复问题
- 重新运行命令
- 只有通过才继续

### 5. 最终验证

完成前：

- ✅ 计划中的所有任务已完成
- ✅ 所有测试已创建并通过
- ✅ 所有验证命令通过
- ✅ 代码遵循项目约定
- ✅ 文档已按需添加/更新

## 输出 — 写一份实现报告

把一份简短报告写到 `docs/ai/reports/<plan-slug>-report.md`（并打印摘要）。PR 正文和 `piv-review-pr` 门禁都会读取它——尤其是**偏离（deviations）**（记录过的偏离是*有意*决策，评审者不应再标记）：

```markdown
# 实现报告 — <特性>

**计划**：<路径>   **分支**：<feature/...>   **状态**：COMPLETE（完成）| PARTIAL（部分）

## 摘要
{构建了什么，2-4 句话。}

## 已完成任务
- [任务] → `path/to/file`（CREATE/UPDATE）

## 新增测试
{测试文件 + 用例 + 结果。}

## 验证结果
{类型检查 / lint / 测试 / 构建 — 通过/失败及计数。}

## 与计划的偏离
{相对计划改了什么以及为什么——或 "无"。这是评审者的意图信号。}

## 遇到的问题
{任何值得注意的事，或 "无"。}
```

### 为下一步做好准备
- 确认所有更改完整且验证通过。
- 下一步：用 `piv-commit` 提交工作，然后 `piv-create-pr` 开 PR（报告填充 PR 正文），然后 `piv-review-pr`。

## 备注

- 如果遇到计划未处理的问题，记录它们
- 如果需要偏离计划，解释为什么
- 如果测试失败，修复实现直到它们通过
- 不要跳过验证步骤
