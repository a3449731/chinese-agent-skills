# 调查 Issue #$ARGUMENTS（根因分析）

## 目标

调查本仓库的 GitHub issue #$ARGUMENTS，识别根因，并为后续实现记录发现。

**前置条件：**
- 在带有 GitHub 远程仓库的本地 Git 仓库中工作
- GitHub CLI 已安装并认证（`gh auth status`）
- 来自本仓库的有效 GitHub issue ID

## 调查流程

### 1. 获取 GitHub Issue 详情

**使用 GitHub CLI 检索 issue 信息：**

```bash
gh issue view $ARGUMENTS
```

这会获取：
- Issue 标题和描述
- 报告者和创建日期
- 标签和状态
- 评论和讨论

### 2. 探索代码库——并行展开

**并行**派发专门 AI 助手（一条消息并行多个子代理；Qoder 中用 Agent 工具），让探索快速进行，并把嘈杂的搜索挡在主上下文之外：
- **`codebase-analyst`** — 追踪受影响的代码端到端如何工作：集成点、数据流、状态/副作用、错误处理。返回精确的 `file:line` 引用，不给建议。
- **`research-agent`**（第二个探索者）— 找到相关代码在哪里 + 可借鉴的模式：issue 中的错误字符串、相关函数/模块、类似实现、现有测试模式。

在形成根因之前，把它们的发现合并成一张简短地图（`file:line` + 每处为何重要）。*（这就是并行子代理扇出，应用于诊断。）*

### 3. 审阅近期历史——它是什么时候引入的？

检查受影响区域的近期更改，并确定 bug 是何时进入的：
!`git log --oneline -20 -- [相关路径]`
```bash
git blame -L <起>,<止> <受影响文件>   # 谁/何时引入了可疑行
```
决定：近期**回归** vs **长期存在**的 bug vs **原始**行为——它同时改变修复方式和风险。

### 4. 调查根因——带证据的 5 Whys

不要停在症状上。沿着 **why → because** 链条追问，直到抵达具体、可修复的代码，并为**每一环**附上 `file:line` 证据：
```
WHY <症状> 会发生？  → 因为 <原因A>   （证据：file.ts:123 — <片段>）
WHY <原因A>？      → 因为 <原因B>   （证据：file.ts:456 — <片段>）
… 根因：<要改变的确切代码/逻辑>  （证据：file.ts:789 — <片段>）
```
留意：输入验证缺口、未处理的边界情况、竞态/时序问题、错误假设、缺少错误处理、集成不匹配。

### 5. 评估影响

**确定：**
- 这个问题有多普遍？
- 哪些功能受影响？
- 有变通方案吗？
- 严重度如何？
- 会导致数据损坏或安全问题吗？

### 6. 提出修复方案

**设计解决方案：**
- 需要改什么？
- 哪些文件会被修改？
- 修复策略是什么？
- 有替代方案吗？
- 需要什么测试？
- 有任何风险或副作用吗？

## 输出：创建 RCA 文档

把分析保存为：`docs/issues/issue-$ARGUMENTS.md`

```markdown

```

## 把摘要发布到 issue 上

写完文档后，把简短版本作为 GitHub 评论发布——既是审计轨迹，也让修复可以从 issue 本身触发/跟踪：
```bash
gh issue comment $ARGUMENTS --body "<标题 · 评估表（严重度/复杂度/置信度 + 一句话理由）· 1-2 行根因 · 要改的文件 · 下一步：/piv-implement-issue $ARGUMENTS>"
```

## 边界情况

- **issue 已关闭** → 如实报告；如果仍需要分析，照常写 RCA。
- **已有链接的 PR** → 先警告；继续前确认。
- **无法定位根因** → 设置 **Confidence: LOW**，记录最佳假设和不确定之处，并在任何修复前标记出来让人确认。
- **范围太大** → 建议拆分成更小的 issues；让这份 RCA 聚焦核心问题，把其余列为范围外。
