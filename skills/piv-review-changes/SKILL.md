# 代码评审（Code Review）

对最近更改的文件执行技术代码评审。

## 核心原则

评审理念：

- 简洁是极致的复杂——每一行都应证明自己存在的价值
- 代码被阅读的次数远多于被书写的次数——为可读性优化
- 最好的代码往往是你没写的代码
- 优雅源于意图的清晰和表达的经济

## 评审什么

先收集代码库上下文，理解代码库的标准和模式。

从检查以下内容开始：

- CLAUDE.md
- README.md
- 核心模块中的关键文件
- docs 目录中的文档化标准（以及项目声明的参考资料，如 `.claude/references/`、`.qoder/rules/`）

有了良好理解后，运行这些命令：

```bash
git status
git diff HEAD
git diff --stat HEAD
```

然后检查新文件列表：

```bash
git ls-files --others --exclude-standard
```

完整阅读每个新文件。完整阅读每个更改过的文件（不只是 diff），以理解完整上下文。

对每个更改的文件或新文件，分析：

1. **逻辑错误**
   - Off-by-one 错误
   - 错误的条件判断
   - 缺少错误处理
   - 竞态条件

2. **安全问题**
   - SQL 注入漏洞
   - XSS 漏洞
   - 不安全的数据处理
   - 暴露的密钥或 API keys

3. **性能问题**
   - N+1 查询
   - 低效算法
   - 内存泄漏
   - 不必要的计算

4. **代码质量**
   - 违反 DRY 原则
   - 过度复杂的函数
   - 命名不佳
   - 缺少类型提示/注解

5. **符合代码库标准与既有模式**
   - 符合 docs 目录中记录的标准
   - Lint、类型和格式化标准
   - 日志标准
   - 测试标准

## 验证问题真实存在

- 为发现的问题运行特定测试
- 确认类型错误是真实的
- 结合上下文验证安全担忧

## 输出格式

把新文件保存到 `docs/ai/code-reviews/[合适的名称].md`

**统计：**

- 修改的文件：0
- 新增的文件：0
- 删除的文件：0
- 新增行数：0
- 删除行数：0

**对每个发现的问题：**

```
severity（严重度）: critical|high|medium|low
file（文件）: path/to/file.py
line（行）: 42
issue（问题）: [一句话描述]
detail（细节）: [解释为什么这是个问题]
suggestion（建议）: [如何修复它]
```

如果未发现问题："Code review passed. No technical issues detected."（代码评审通过。未检测到技术问题。）

## 重要

- 要具体（行号，而不是模糊的吐槽）
- 聚焦真实 bug，而不是风格
- 建议修复，而不只是抱怨
- 把安全问题标记为 CRITICAL
