# /piv-slice-epic — 把 Epic 切成 PIV 大小的 Ticket

战略文档与 PIV 循环之间的桥梁。epic 文档是目的地；PIV 循环是推进的单位；**ticket 是桥梁。** `/piv-slice-epic` 负责切片。

## 输入

- `$ARGUMENTS` — 要切的 **epic 及其架构决策**。它们以**一个文档或两个文档**的形式到达：
  - 一个自带 `## Architecture` 章节的已架构 epic，**或**
  - **epic 加一个独立的、链接的架构页面**（架构与 epic 并排存放时的常见情况——例如 Confluence epic 页面及其链接的架构页面，两者都以 URL 传入）。**两个都要读。**
  - 全新项目：PRD 代替 epic。
  当输入是工单系统引用（Confluence/Jira URL 或 key）时，通过 Atlassian MCP 从源头获取。**这是关键输入：** 架构点名了切片必须尊重的接缝、数据模型和缺失部分。
- **不依赖 prime。** 已加载上下文的会话有帮助，但不是必需的。如果代码库表面尚未加载，本技能会在切片前自行定位（步骤 2）。

## 流程

### 步骤 1 — 阅读来源

完整阅读 epic（目标、用户故事、验收标准、非目标）**及其架构决策，无论它们是 epic 上的 `## Architecture` 章节，还是独立链接页面**（方案、技术栈、数据模型、缺失部分、spikes）。如果架构是独立页面，也获取并阅读它。切片必须尊重那些决策。

### 步骤 2 — 在代码表面定位（如果尚未加载上下文）

切片需要足够的代码库意识来判断什么独立、什么依赖——文件重叠、共享接缝。如果会话已经定位过，跳过此步。否则**自己探索——不要依赖之前的 `/prime-codebase`**：从架构点名的接缝、数据模型和缺失部分出发，阅读相关文件/目录（例如适配器接口、编排器、摄取管道），看看什么已存在、什么被复用、新代码落在哪里。足以自信地切片即可——不需要完整的重新推导。

### 步骤 3 — 分解成 PIV 大小的切片

把 epic 拆成 ticket。**按 AI 的规模来切，而不是按人类 backlog 的习惯**——一个 AI 循环承载的能力远超传统 ticket：一个小到中等的实现*阶段*，约 8–10 个子任务，通常是 **500–1500 行改动（20–50% 是测试）**。小 epic 甚至可能就是一个 ticket。一个尺寸良好的 ticket：

- 是**一个可测试的关注点**——能独立地**测试、评审、证明**。
- 是一个连贯的单位——行为的垂直切片，不是水平层。
- 有自己的清晰验收标准。
- 足够小，**一次专注的循环就能不丢失上下文地一次完成**——不至于大到 AI 助手丢失主线、效果递减。

按**依赖**、按**关注点**、或作为**细端到端切片**来拆分（先薄薄地证明整个流程，下一轮再增厚）——无论哪种都让每个 ticket 最容易证明。如果一个切片大到无法在一次诚实的通过中测试或评审，就进一步拆分。*规划的细节*无论如何都保持高层——更大的是*范围*。

### 步骤 4 — 为并行化切片

映射 ticket 之间的依赖。**独立 ticket**——不触碰相同文件、不依赖彼此输出的——可以在**并行 worktree** 中运行（见 `/worktree-create`）。标记哪些 ticket 独立、哪些构成依赖链。沿着垂直切片架构的接缝切，能最大化独立性。

**Just-in-time 规划：** 依赖 ticket 要等它的依赖被*实现*（而不只是被切好）——构建依赖会为依赖者的规划提供信息，所以提前规划等于对着猜测规划。独立 ticket 可以并行规划和运行；依赖 ticket 排队等待。

### 步骤 5 — 写出 ticket 分解

把 ticket 写入你的工单系统（通过 Atlassian MCP 的 Jira、Linear、GitHub Issues、Archon 的 tasks）——如果你是单人开发、没有工单系统或未配置 Atlassian MCP，就写入本地 `docs/tickets/<epic-slug>.md`。无论哪种，**每个 ticket 都自带上下文**——这正是让循环之后无需重读整个 epic 就能拾起它的原因：

```
# Ticket 分解 — <epic 名>

## Epic 摘要 — 2-3 行目标
## Tickets
   ### TICKET-1 — <标题>
   - 范围 / 验收标准 — 一个可测试的关注点
   - 每个 ticket 的上下文：该 ticket 需要的文档章节、指南和接缝
     （例如 "source-adapter 指南 · 接缝：adapter interface · epic 的 AC #2 + #4"）
   - 涉及文件（估计）· 大致规模（~500–1500 行，含测试）
   - 依赖：<无 / TICKET-x>
   ### TICKET-2 — ...
## 依赖图
   <文本或 mermaid 图，显示顺序 + 并行分组>
## 建议执行顺序
   波次 1（并行）：TICKET-1, TICKET-3
   波次 2：TICKET-2（在 TICKET-1 实现之后）
```

## 输出

在你的工单系统中（或 `docs/tickets/<epic-slug>.md`）得到一份 ticket 分解。每个 ticket 随后进入自己的 PIV 循环——如果范围良好就直接去 `/piv-plan-implementation`（它会自行加载所需的上下文），或者如果需要更多代码库定位就先去 `/prime-codebase`。**Prime 是可选的；** 上面的每个 ticket 自带上下文，正是让这一点成为可能的原因。

## 备注

- 问题管理是**工具无关的**：Jira（通过 Atlassian MCP）、Linear、Notion、GitHub Issues、Archon 的 tasks——或者如果你是单人开发，就是一文件夹的 markdown 文件。工单系统不重要；目标是**把工作切得刚好让每个循环都有最高的概率一次成功，这样你就可以自动化这个循环。**
- 全新项目：同样的切片适用于 MVP 阶段而不是 epic tickets。
