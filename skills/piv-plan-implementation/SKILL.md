# 规划一个新任务

## 特性：$ARGUMENTS

## 先解析输入

`$ARGUMENTS` 有两种可能：**工单系统的 ticket**（如 `ACC-30` 这样的 key，或 Jira / Linear / GitHub 的 issue URL），或**自由描述的特性需求**。先区分类型，再分别处理：

- **ticket**（如 `ABC-123` 这样的 key，或 issue URL）：**规划之前先从工单系统获取它**（Jira 通过 Atlassian MCP，GitHub 通过 `gh issue view` 等），阅读其摘要、验收标准和单票上下文。然后**顺着链接向上找到 epic 及 epic 链接的架构页面**（Confluence 通过 Atlassian MCP），继承其中的决策（见下文"继承，不重新决策"）。绝不只凭一个孤零零的 key 就规划——ticket 正文、它的 epic 和架构才是真正的输入。
- **自由描述**：直接基于它规划（全新项目或临时任务），必要时提出澄清问题。

## 使命

通过系统性的代码库分析、外部调研和战略规划，把一个特性请求转化为**全面的实现计划**。

**核心原则**：本阶段不写代码。目标只是创建一份上下文丰富的实现计划，让 AI 助手能一次成功实现。

**关键理念**：上下文为王（Context is King）。计划必须包含实现所需的全部信息——模式、必读文件、文档、验证命令——让执行方第一次尝试就成功。

**继承，不重新决策（Inherit, don't re-decide）**：这是**按 ticket** 制定的计划。如果该 ticket 属于已有架构决策的 epic——**链接的架构页面**（例如 `plan-architecture` 技能产出的 Confluence 页面，从 ticket 的 epic 可以到达）、epic 上的 `## Architecture` / `## Engineering` 章节、或本地 `architecture.md` / `engineering-plan.md`——**先读它**，把其中的横切决策（技术栈与版本、数据模型、安全边界、新代码插入的接缝）视为**已定案**。继承即可，不要重新讨论。只需规划 ticket 层面剩余的内容：具体文件、要模仿的局部模式、测试。如果某个 ticket 确实需要打破 epic 级决策，把它写进开放问题（Open Questions）里，而不是静默偏离。

## 规划流程

### 阶段 1：特性理解

**深度特性分析：**

- 提炼要解决的核心问题
- 识别用户价值和业务影响
- 确定特性类型：新能力（New Capability）/增强（Enhancement）/重构（Refactor）/Bug 修复（Bug Fix）
- 评估复杂度：低/中/高
- 映射受影响的系统和组件

**创建用户故事格式（如果用户已提供故事则精炼它）：**

```
作为 <用户类型>
我想要 <行动/目标>
以便 <收益/价值>
```

### 阶段 2：代码库情报收集

**善用专门子代理和并行分析：**

**1. 项目结构分析**

- 检测主要语言、框架和运行时版本
- 映射目录结构和架构模式
- 识别服务/组件边界和集成点
- 定位配置文件（pyproject.toml、package.json 等）
- 找到环境设置和构建流程

**2. 模式识别**（有益时使用专门子代理）

- 在代码库中搜索类似实现
- 识别编码约定：
  - 命名模式（CamelCase、snake_case、kebab-case）
  - 文件组织和模块结构
  - 错误处理方式
  - 日志模式和标准
- 提取该特性领域常见模式
- 记录要避免的反模式
- 检查 CLAUDE.md 中的项目特定规则和约定

**3. 依赖分析**

- 盘点与特性相关的外部库
- 了解库如何集成（检查导入、配置）
- 在 docs/、ai_docs/、.qoder/rules/ 或 ai-wiki（如可用）中找到相关文档
- 记录库版本和兼容性要求

**4. 测试模式**

- 识别测试框架和结构（pytest、jest 等）
- 找到可参考的类似测试示例
- 了解测试组织（单元 vs 集成）
- 记录覆盖率要求和测试标准

**5. 集成点**

- 识别需要更新的现有文件
- 确定需要创建的新文件及其位置
- 映射路由/API 注册模式
- 了解数据库/模型模式（如适用）
- 识别认证/授权模式（如相关）

**澄清歧义 — GATE（门禁）：**

代码库分析已完成，开放问题此刻变得*具体*。这是你既了解得够多、问得出好问题、又还没写任何东西的唯一时机。**GATE** 的意思是：抛出问题，然后停下。结束本轮对话，等待回答。不要在同一轮里既问又答，也不要直接进入阶段 3。

一次性提出**一组**编号问题，最多 3-6 个，每个都附上**推荐默认值**，让回答成本很低（"除非你另有说明，否则我按第一个来"）。问题只能来自分析真正留下的空白：

1. **范围边界** — 一个合理读者会认为在范围内的相邻事项。确认它不在范围内。
2. **模式分叉** — 两个既有模式都适用。同时点出两者并附 `file:line`，问镜像哪一个。
3. **契约形态** — ticket 暗示但从未明说的 API 表面、载荷或数据模型变更。
4. **失败行为** — ticket 对错误路径保持沉默时会发生什么。
5. **偏好** — 一个在本代码库中没有先例可继承的库或权衡。
6. **完成定义** — 一个缺失的验收标准，或写得无法核对的验收标准。

没有真正开放项的类别就跳过；绝不为了凑数而编造问题。如果 ticket、它的 epic 和架构文档确实把所有事都定下来了，用一行说明并继续。沉默不等于放行。

**含糊的回答：** 把模糊的回答还原成它悬而未决的具体选择（"'优雅地处理错误'——是返回 4xx 加消息，还是重试后 503？"），再问一次。绝不把含糊回答当成确定结论写进计划。

**如果对方拒绝**（"直接写吧"）：尊重这个选择，但要明确指出你在猜测什么。每个未回答事项都变成 `OPEN QUESTIONS / ASSUMPTIONS` 中的一行 `Assumed — <假设内容>, confirm before execution`（假设 — <内容>，执行前确认），受其影响的任务带上点名该假设的 **`GOTCHA`**。绝不静默猜测。

**上游已定：** ticket、其 epic 或链接架构页面已经回答的任何事都不是开放项。继承它并跳过（见"继承，不重新决策"）。

### 阶段 3：外部调研与文档

**外部调研有益时使用专门子代理：**

**文档收集：**

- 调研最新库版本和最佳实践
- 找到带具体章节锚点的官方文档
- 定位实现示例和教程
- 识别常见坑和已知问题
- 检查破坏性变更和迁移指南

**技术趋势：**

- 调研技术栈的当前最佳实践
- 找到相关博客文章、指南或案例研究
- 识别性能优化模式
- 记录安全考量

**汇总调研引用：**

```markdown
## 相关文档

- [库官方文档](https://example.com/docs#section)
  - 特定功能实现指南
  - 原因：实现 X 功能所需
- [框架指南](https://example.com/guide#integration)
  - 集成模式章节
  - 原因：展示如何连接组件
```

### 阶段 4：深度战略思考

**深入思考：**

- 这个特性如何融入现有架构？
- 关键依赖和操作顺序是什么？
- 什么可能出错？（边界情况、竞态条件、错误）
- 这将如何被全面测试？
- 有什么性能影响？
- 有安全考量吗？
- 这个方案的可维护性如何？

**设计决策：**

- 在替代方案之间选择，附清晰理由
- 为可扩展性和未来修改而设计
- 如有需要，规划向后兼容
- 考虑可扩展性影响
