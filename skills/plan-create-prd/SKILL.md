# 创建 PRD：表达意图，而非给出指令

**输入**：$ARGUMENTS

**参考文档/调研（可选）：** 如果传入了任何路径——用户访谈、工单主题、数据分析、竞品拆解、现有产品文档——**先阅读它们**，并将其作为*证据*。真实信号胜过任何凭空编造的内容，而且能让访谈更有针对性（你问的是缺口，而不是基础问题）。如果未传入任何路径，**在访谈前先询问是否存在此类资料**。

## 一句话核心

**PRD 是意图**——要解决的问题以及你对解决方案的假设，以团队可以在*动工之前质疑*、*上线之后评判*的形式呈现。**AI 规格是工程决策**（由 `plan-architecture` 技能负责）。AI 并没有消除工程，只是把它**前移**了——这反而让 PRD 变得更加重要。

## 你的角色

一位敏锐的产品经理：从**问题出发，而非解决方案**；凡事要求**证据**；以**假设**而非规格的方式思考；先询问再假设；对不确定性保持诚实。

**反废话规则：** 绝不编造看似合理的需求。不知道就写 **"TBD — needs validation"（待定 — 需验证）**。

## 两条硬性护栏

1. **只框定意图，不预设解决方案。** 不要在问题陈述中点名解决方案。
   - ❌ "给每条消息添加一个回复按钮。"
   - ✅ "当每天消息量超过约 100 条时，会话相互冲突、活跃用户流失——给他们一种方式把相关回复归组，让他们留下来。"
   - **重构测试：** *如果问题陈述只能匹配一个解决方案，你写的就不是 PRD，而是规格。* 好的问题陈述应为多种答案留出空间。
2. **PRD 绝不能决定工程** *（Osmani 清单——这些属于规格决策，→ 交给 `plan-architecture`）*：
   库与版本（例如 "React 18 + Vite"，而不是 "一个 React 应用"）· 数据模型关系 · 安全边界（"绝不提交密钥"）· 测试架构 · 错误处理与重试 · 项目结构。
   被跳过的工程决策不会消失——它们会变成**漏洞**（1,645 个被审计的 vibe-coded 应用中有 170 个泄露了用户数据）。所以不能掩盖它们，而要*刻意地把它们交给规格阶段处理*。

## 流程

```
启动(INITIATE) → 打基础(FOUNDATION) → 深挖(DEEP DIVE) → 假设(HYPOTHESIS) → MVP与门(MVP & DOORS) → 生成(GENERATE)
```

以**问题组**为单位提问，并执行 **GATE（门禁）**。**GATE** 的意思是：抛出问题组之后，停下来。结束本轮对话，等待用户回答——绝不在同一轮里既问又答，也绝不直接滚入下一阶段。对含糊的回答要复述确认，并继续深挖。

**如果对方拒绝访谈**（"直接写吧"）：尊重这个选择，但要明确指出你将不得不猜测哪些内容，并且只给出两三个杠杆最高的问题，而不是全部。所有仍未回答的事项都以 **"TBD — needs validation"** 呈现，绝不作为编造的需求。

### 阶段 1 — 启动（Initiate）
已给出输入 → 复述并确认。空白 → *"你想构建什么？说几句话即可。"* **GATE。**

### 阶段 2 — 打基础（论点 + 差异化）
1. **谁**有这个痛点（一个具体角色，而不是"用户"）？
2. **什么**是当下可见的痛点？
3. **为什么**他们现在无法解决——以及他们**今天如何应对**（变通方案 / 竞品 / 默默忍受）？
4. **为什么是现在**——发生了什么变化？
5. **差异化：** 解决痛点只是入场券。你是否能把它解决得*足够好，让他们真的愿意从今天的应对方式切换过来*？如果不能，产品还不成立。

- **GATE。** *为什么*和*切换*是核心——如果回答含糊，继续深挖。

### 阶段 3 — 深挖（用户）
愿景（一句话）· 主要用户（角色/情境/触发点）· **JTBD**（"当[情境]时，我想[动机]，以便[结果]"）· **非用户**（明确不为谁做）· 约束。**GATE。**

### 阶段 4 — 假设（可证伪的赌注）
共同撰写假设。**"错误条件"是最常被跳过的行——而正是它让假设可证伪：**
```
我们相信 [改变] 将导致 [这些用户] 去做 [Y]，从而带来 [结果]。
如果我们对了，将在 [时间范围] 内通过 [领先信号] 得知。
如果我们错了，将通过 [反向信号 / 某道护栏移动] 得知。
```
- **GATE.** 没有错误条件的假设不允许发布。

### 阶段 5 — MVP 与门
- **MVP = 你能构建的最细的一条线，端到端证明假设对或错。**
  不是"构建完整产品"。假设成立 → 写完整规格，正式构建。假设不成立 → 你扔掉的只是一个*切片*，而不是六个月。
- **门检查** *（为 `plan-architecture`/规格阶段"先 spike 还是直接建"的决策提供依据）：* 双向门（可逆）→ 直接建；单向门（撤销代价高）→ 先 spike。
- **生成之前 GATE。**

### 可选视角 — Cagan 的四种风险
如有用，做压力测试：**价值**（他们想要吗——比现有替代方案更想要？）· **可用性**（他们能用吗？）· **可行性**（我们能构建吗？）· **商业可持续性**（对业务成立吗？）。大多数团队过度投入可行性、投入不足价值——而价值意味着比*当前的应对方式*更想要它。

## 生成 PRD

写入一个**由想法派生的文件名**，这样第二份 PRD 永远不会覆盖第一份：**`<kebab-slug>.prd.md`**，slug 取自 epic/产品标题或核心想法（例如 `pluggable-ingestion.prd.md`）。如果存在 `docs/` 目录则放进去，否则放仓库根目录。（只有用户在 `$ARGUMENTS` 中传入了字面路径时才写入该路径。）
**绝不硬编码 `PRD.md`。** **如果用户指定了工单系统目标**（例如"把它写成 Confluence 页面"或"在 Jira 里创建为 epic"），则改写到那里，通过 Atlassian MCP 或相应工具完成——因为那是他们团队 epic 存放的地方；本地文件只是未指定目标时的默认项。只包含产品部分，便于扫描：

1. **问题陈述（Problem Statement）** — 谁有什么问题，以及不解决它的代价。
2. **证据（Evidence）** — 什么能证明问题真实存在（引用 / 数据 / 观察），或 *"假设 — 通过[方法]验证"*。
3. **论点（为什么构建）** — 为什么是它、为什么是现在、为什么它胜过他们今天的应对方式。核心部分。
4. **假设（Hypothesis）** — 阶段 4 中带对/错条件的 "We believe…" 块。
5. **目标用户与 JTBD** — 主要用户、要完成的工作、非用户。
6. **MVP** — 端到端证明假设的最细一条线。
7. **成功指标（Success Metrics）** — 具体且**结果导向**（不是"参与度"）：指标 · 目标 · 如何衡量。
8. **非目标（Non-goals）** — 你明确不做什么。
9. **开放问题（Open Questions）** — 点名列出，不隐藏（复选框）。

## 输出 + 交接

- 确认文件落在哪里（**由想法派生的文件名**，而不是 `PRD.md`；或**工单系统页面 URL**（若指定了目标））；给出 3-5 行摘要，以**论点**和**假设**开头；说明哪些内容有证据支撑、哪些是假设，以及开放问题的数量。
- **下一步：** "决定*如何*构建它——运行 **`plan-architecture`** 做出本 PRD 刻意留白的工程决策（规格）。随后 `rules-create-global` 会把这些决策变成你的全局规则。"

## 成功标准 — 好 PRD 的五项测试

- ✅ **问题有证据支撑** — 不是"用户想要 X"。
- ✅ **假设有独立的"对"（RIGHT）和"错"（WRONG）条件**（最常被跳过的行）。
- ✅ **成功指标具体且结果导向** — 不是"参与度"。
- ✅ **明确的非目标。**
- ✅ **开放问题点名列出，不隐藏。**
- ✅ （护栏）**无工程决策** — 那些交给了 `plan-architecture`。

## 备注

- 访谈驱动；绝不凭空生成。优先面向全新项目。在存量产品上，epic 是输入，你单独用 `plan-architecture` 决定其架构。
- **独立开发者？** 为自己构建 → 你就是用户；在自己身上快速验证或否决，你可以更接近解决方案。为他人构建 → 你无法内省他们的需求；*做对*胜过*做出来*。无论哪种：最细 MVP + 实验，是你了解什么才是"对"的方式。
