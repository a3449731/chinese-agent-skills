# 创建保证层：把一个想法变成接入仓库的确定性守卫

**用户希望保证层做什么**：$ARGUMENTS

若已填好，就把它当作行为规格，从这里开始。不要重复询问用户已告知的内容，只为钉死缺口而问——确切的路径/命令/模式，以及它是否必须*阻止*。若为空，则从询问"这条保证要保证或做什么"开始（工作流第 1 步）。

## 什么是保证层（30 秒简介）

**保证层**是挂在仓库既有工作流关卡上的确定性代码：提交时、推送时、合并前——关卡一到便自动触发。与规则不同，**任何人或 AI 助手都无法"选择"绕过它**（除非主动禁用钩子本身）。这正是关键：规则只是*请求*照做；保证层在版本控制的工具层上**强制**做到。

- **git 钩子**（pre-commit / pre-push / commit-msg）：跨工具、跨 AI 助手生效，是默认选择。
- **CI 门禁**（GitHub Actions check）：本地钩子可被 `--no-verify` 绕过，CI 是补位的第一道。
- **Claude Code hooks**（`.claude/settings.json`）：仅当用户在会话内、对 AI 助手的动作做实时阻止时才需要——见 [references/layers.md](references/layers.md) 的专属分支。
- **诚实的边界**：`.qoder/rules/`、AGENTS.md 这类 IDE 规则是**软约束**——它们引导而非强制。用户想要"绝不发生"级别的保证时，不要拿规则充数。

用户带来**想法**（"谁都不许把 `.env` 提交进来"）；本技能负责写**代码**并把它接进去，用户不需要懂 Python。

## 唯一要搞对的事：哪个保证层，以及它能阻止吗？

用户想要的行为映射到**一个**保证层。按*何时*触发以及*是否必须阻止某事*来选：

| 用户目标 | 保证层 | 能阻止吗 |
|---|---|---|
| 阻止提交机密/受保护路径/超大文件 | git **pre-commit** 钩子 | **能**——阻止提交发生 |
| 测试 / lint / 类型检查未绿不许推送 | git **pre-push** 钩子（或 CI） | **能**——阻止推送 |
| 提交消息规范（如 conventional 格式） | git **commit-msg** 钩子 | **能**——拒绝该次提交 |
| 合并前最后防线（本地钩子可被绕过） | **GitHub Actions** check | **能**——阻止合并 |
| 会话内实时阻止 AI 助手的动作（Claude Code 用户） | `.claude/settings.json` hooks（PreToolUse/Stop 等） | **能**——见 layers.md 分支 |
| 引导 AI 助手日常行为（非强制） | `.qoder/rules/`、AGENTS.md | **不能**——软约束，如实告知用户 |

> **先本地关卡，再 CI 补位。** 若目标是"确保 X 绝不进仓库"，选 pre-commit；若目标是"不绿不许出门"，选 pre-push 或 CI；若两者都要（机密 + 质量），可组合，但一次只建一层、逐个证明。

## 工作流

### 1. 理解想法（从 `$ARGUMENTS` 开始；只为补缺口而问）

从用户已描述的内容出发（用户可能不懂技术）。用平实的语言钉死两件事，只问缺失的部分：

- **什么**应该发生或被阻止，以及**何时**（提交时 / 推送时 / 消息检查 / 合并前）？
- **匹配要多精确？**（"任何 `.env` 文件"、"`migrations/` 目录"、"测试命令退出非零"）。要拿到具体的路径/命令/模式——保证的好坏取决于它匹配什么，所以不要猜。若请求含糊，提出一个具体的解释并请用户确认。

### 2. 挑选保证层

用上面的映射表选一层。仓库已有 husky（存在 `.husky/` 目录）就走 husky；否则用原生 `.git/hooks` + `core.hooksPath` 指向版本控制的目录——接入细节照抄 [references/layers.md](references/layers.md)，不要凭记忆。

### 3. 编写守卫脚本

- 默认放目标仓库 `scripts/guards/<hook_snake_case>.py`，**纯标准库 python3**（不依赖 uv/venv，钩子环境里什么都没有）。骨架从 [scripts/guard_template.py](scripts/guard_template.py) 抄，它已内置 fail-open 与三种钩子模式。
- 脚本顶部放**用户唯一需要编辑的常量**（被禁模式、测试命令、消息正则），一眼可见。
- **故障开放（fail open）。** 把正文包起来，让任何意外错误都退出 0 并打印警告——坏掉的守卫绝不能把用户锁在提交之外。唯一有意的非零退出是刻意的阻止，必须带清晰的 stderr 原因。
- 若该钩子已有内容（如 `.husky/pre-commit` 已跑 lint），**追加**你的守卫调用而不是覆盖。

> ### ⚠️ 从守卫运行项目命令（写之前先读这个）
>
> 守卫脚本的解释器**没有**项目的依赖。所以：
>
> - **绝不**用 `sys.executable` 或裸的 `["python", "-m", "pytest", ...]` 重建命令——那会运行守卫自己的解释器，它没有项目依赖，命令会每一次都以 `No module named …` 失败，于是"测试通过前不许推送"的守卫会在绿灯上像在红灯上一样轻易地阻塞，并报出一个无意义的原因。
> - **要**把用户的命令**逐字作为 shell 字符串，在仓库根目录运行**。Node 项目优先走包管理器脚本（`npm test`），Python 项目若存在 `.venv`/`venv` 则把它的 `bin` 放到 `PATH` 最前。照抄模板里的 `_run_project_command()`，不要自行发挥。
> - 若命令必须从**子目录**运行（monorepo），问清楚并把 `cwd` 指过去。搞错会产生一个永远阻塞的守卫，用户会把它读成"钩子坏了"。

### 4. 接入保证层

按 layers.md 对应小节的步骤接入（husky 文件 / `core.hooksPath` / workflow YAML）。接入后确认钩子文件有可执行权限。

### 5. 自己证明它，然后解释并警告

**交出前先运行守卫。** 不要交付一个你只读过、没跑过的守卫——一个总是阻塞、或从不阻塞的守卫，在错误的时刻触发之前，看起来与正常的守卫一模一样。

- **双向验证（强制）**：构造一个*应该被阻止*的场景（把 `.env` 加入暂存、让测试故意失败）确认退出非零；再构造一个*应该放行*的场景确认退出 0。两个方向都测过才算交付。
- 对**运行命令的守卫**（测试门），确认命令通过时退出 0、真正失败时退出非零。若两种状态都退出非零，命令没有正确解析——重读第 3 步的 `sys.executable` 警告。
- 然后用大白话告诉用户**你建了什么**：哪个保证层、它保证什么、以及他们为调整它而要改的那一行。
- **诚实标注边界**：本地钩子可以被 `git commit --no-verify` 绕过——所以对"不可妥协"的保证，建议同时有 CI 补位；匹配器的*覆盖范围*只与它本身一样好（例如 `.env` 匹配器抓不到把机密粘贴进别的文件）。
- **安全提示（每次都讲）**：钩子会在每次匹配时自动运行代码。要像审查 CI 配置一样审查守卫脚本，只保留你信任的。

## 质量检查

- 行为映射到**正确的保证层**，阻止型目标用能阻止的层——不是拿 IDE 规则充数。
- 守卫脚本**纯标准库、故障开放**；唯一的非零退出是预期的阻止，带清晰的 stderr 原因。
- 任何**项目命令通过 `shell=True` 在仓库根（或约定子目录）逐字运行**——绝不通过 `sys.executable` 重建。
- 已有钩子内容是**追加**的，不是覆盖的；钩子文件有可执行权限。
- **双向验证跑过**：该拦的场景拦住了，该放的场景放行了——不只是读过它。
- 用户得到了**大白话解释 + `--no-verify` 边界 + 安全提示**。

## 备注

- 保证层是仓库的确定性底线——用它们处理不可妥协的事（机密、受保护路径、"不绿不许出门"），而不是规则就能处理好的事。
- 保持守卫快——它们在每次提交/推送时都运行。重活（完整 e2e）留给 CI。
