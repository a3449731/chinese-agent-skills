# 给运行打分

消融最难的部分不是删除东西。是看清你失去了什么。

**每次运行看起来都很好。** 被剥离的 AI 助手不会产出坏代码。它产出的代码能编译、读起来不错、能通过评审。差别在于它不知道去做的事。

所以永远不要问"被剥离的运行失败了吗？"它没有。改成逐条规则打分。

---

## 按规则打分，不要按 diff 打分

把一次对照运行和一次剥离运行做 diff 是显而易见的做法，也是个坏做法。同一任务的两个独立实现在一百个无关的方面不同，而重要的差异淹没在不重要的差异里。

改成把总是加载的文件变成一个编号的**可测试声明**清单，然后对每条声明评判每次运行。

一条可测试的规则命名你能在 diff 里看到的东西：

- "每个公开函数都装饰了 `@tracked`"是可测试的。
- "写干净、可维护的代码"不是。把它标为 `unfalsifiable`（不可证伪）然后继续。它本来就活不过实验，这件事本身就值得报告。

对每个 (run, rule) 对，恰好记录以下之一：

| 裁决 | 含义 |
|---|---|
| `followed` | diff 明显符合 |
| `violated` | diff 明显违反 |
| `n/a` | 这个任务从没给这条规则应用的机会 |

## 盲评

不要告诉评分者某个 diff 来自哪一臂，也不要在读出 CLAUDE.md 规则文本的同时评那个 diff。知道一个 diff 是"被剥离的那个"就足以让违规显现。打乱 diff，评分，然后把裁决接回它们的臂。

## 然后跨运行读模式

只有现在才把两臂合回来。对每条规则，比较它在每臂里被遵循的频率：

| 模式 | 它意味着什么 | 行动 |
|---|---|---|
| 对照遵循，剥离违反 | **承重。** 这条规则在做真实的工作。 | 保留它。重写得更短更具体。 |
| 两臂都遵循 | 模型本来就会这么做。规则没买到任何东西。 | 删除它。 |
| 两臂都违反 | 这条规则*即使加载了*也被无视。 | 不要只是删除。如果它重要，把它移进 hook、测试或 lint 规则。如果不重要，删除。 |
| 从不适用 | 这个任务从没锻炼它。**两边都没有证据。** | 保留它，并标记为未测试。据此删除是凭信仰删除。 |
| 臂内不一致 | 噪声，不是信号。 | 更多运行，或一个更好的探针任务。 |

第四行是人们搞错的那行。探针任务从没碰过的规则，看起来和没起作用的规则一模一样，而它们意味着相反的东西。作为两个独立清单报告，绝不合并。

## 会咬你的混淆变量

**现有代码替代规则文件。**

在一次验证中，一次剥离运行写了两个文件。在已经包含相似函数的那个文件里，它完美匹配了全部四条家规，从邻居那里抄来的。在那个全新的文件里，没有本地示例，它违反了家规，落回默认值。

同一次运行、同一个缺失的 CLAUDE.md、相反的结果，完全因为屏幕上碰巧有什么。

所以评分时，把**对现有文件的编辑**和**新建的文件**分开。一条只在新建文件里成立的规则不是没价值；它意味着你的代码库已经在用示例教那条约定，而规则是全新项目工作的兜底。那是一个真实发现，和"删除它"是不同的决定。更重地权衡新建文件的证据，并说出每个裁决基于哪种证据。

## 差异实际出现的六个地方

当一条规则模糊时，或当你想找出你从没写下来的规则时，读 diff 找这些。消融差异集中在它们。

**1. 注册和接线。** 最可重复的失败。一个新测试文件没被加进枚举的测试脚本，就永远不会跑，套件保持绿色。还有：模块缺失于 barrel 或导出映射、路由或迁移没注册、env 变量没加进 schema 或 CI 配置。

**2. 生成产物。** 如果仓库从事实源生成代码、schema、文档或 lockfile，编辑源而不重新生成会让树不一致，CI 晚些而不是早些抓住它。

**3. 错误姿态。** 项目对失败有家传立场：早点抛，或安静降级。没有指令的 AI 助手默认产出防御性、宽容的代码。找空的 catch、被吞掉的错误、在仓库会抛的地方返回默认值。

**4. 放置和命名。** 目录布局、测试同居、模块边界。通过读邻居可推导，而这正是没有东西叫它去看时 AI 助手会跳过的事。预料这一条会受上面混淆变量的严重影响。

**5. 设计选择本身。** 最高价值也最容易漏掉的案例，因为两个答案都能用。有些问题有仓库故意排除的明显修复：项目禁止定时器的地方用超时，项目走预设路由的地方用配置字段。问两臂是产出了*同一个设计*，还是两个碰巧都能用的不同设计。

**6. 依赖和工具。** 在仓库有政策的地方加了一个包。一个不同于已经在用的 HTTP 客户端、测试运行器或日期库。

## 重新添加的阶梯

一次重新添加一行，而且只对一条你评了 `load-bearing` 的规则。一条你无法联系到观察到的差异的规则，是一条你凭信仰保留的规则。

按顺序优先：

1. **一条测试或 lint 规则。** 确定性、不能被无视、不花上下文。
2. **一个 hook 或 pre-commit 检查。** 作为代码运行，不花注意力预算。
3. **一条按需指令**（一个技能、一条路径范围的规则），让它只在相关时加载。
4. **一行总是加载的。** 最后手段。它要在这个项目剩下的生命里向每个会话收费。

如果一条规则的存在是为了让模型*推理*得更好，它可能已经过期。如果它的存在是为了让模型*检查*一个它不会想到去检查的东西，它没有。
