# 消融 AI 层

模型升级会悄无声息地让指令退役。为绕过较弱的模型而写的规则，会变成与仍然重要的规则争夺注意力的死重。读文件不会告诉你哪些是哪些。只有实验才能。

**你来运行实验。用户挑选任务并批准结论。**
不要递给用户一列要运行的命令；脚本驱动双臂。

## 什么让结果可信

- **双臂，每臂多次运行。** 被剥离的 AI 助手不会明显失败，所以单次运行没有可比对象，"看起来没问题"就会变成"删掉某个关键的东西"。同一臂的两次运行也可能比两臂之间的差异更大，所以每臂一对是下限，不是目标。
- **什么都不挪走。** 每次运行都在一个从 HEAD 构建、位于仓库外临时目录的分离 git worktree 中进行，之后删除。用户的工作树从不被修改，所以没有需要记得做的恢复步骤。
- **默认只剥离常驻加载集。** 技能、子代理和路径作用域规则在触发前不花任何成本，所以删掉它们不会买回上下文。钩子和权限从不触碰：它们作为代码运行，不消耗注意力。

## 第 1 步：绘制层的全貌

```bash
python <skill>/scripts/map_layer.py [repo_root]
```

只读。把每件产物分类为常驻加载、按需加载和强制（enforcement），并打印常驻加载集在用户输入任何内容之前的每次会话中花费多少。把这个数字给用户看。

如果什么都没找到，说出来并停下。没有什么可测的。

## 第 2 步：获取探针任务

**这是唯一一件你不能替用户决定的事。** 任务决定实验能否检测到任何东西。

一个好的探针任务是用户本来就会做的真实工作，触碰的家规（house conventions）很可能适用的代码，并且要添加一些必须接线的东西：一个测试、一个端点、一个迁移、一个命令。

坏的任务是打错字、重命名或任何一行式修复。它完全可推导，双臂会匹配，用户会错误地得出整个层毫无价值的结论。如果他们提出这样的任务，明说这一点，并要一个约定攸关的任务。

把商定的任务逐字写入一个文件。每次运行都逐字节复用它。

## 第 3 步：展示计划并获得批准

在花费任何东西之前报告：多少次运行、哪个模型、大概要花多少钱、工作树不会被触碰。

```bash
python <skill>/scripts/run_ablation.py <repo> --task-file <task.md> --dry-run
```

预演（dry run）还会浮出两件值得停下来想的事：

- **工作树脏。** Worktree 从 HEAD 构建，所以未提交的编辑不在测试范围内。提议先提交或 stash。
- **构建依赖警告。** 有些仓库把 AI 层当作源代码导入。一个在构建时读取技能 markdown 的 CLI，会在这些文件消失的那一刻坏掉，而用户会把编译错误读成 AI 助手回归。如果这个警告出现，保持 `--scope always`。

## 第 4 步：运行

```bash
python <skill>/scripts/run_ablation.py <repo> --task-file <task.md> --runs 2
```

这就是整个实验。它每次运行建一个全新的 worktree，在被剥离的臂中剥离该层，在每个 worktree 中运行同样的提示词，捕获每个 diff，清理每个 worktree，并把结果写到 `.ablation/<timestamp>/`（gitignored）。

有用的标志：用户打算根据结果行动时用 `--runs 3`；要测试"技能和子代理也已过期"这个更硬的主张用 `--scope all`；`--model`；并发用 `--jobs`；非 Claude 的、从 stdin 读取提示词的 AI 助手用 `--runner`。

如果某一臂没有产出任何可用结果，停下。空臂是坏掉的实验，不是发现。在从中得出任何结论前重新运行。

## 第 5 步：评分

在分析前读取 `references/comparison.md`。它是评分标准，包含区分"真实结果"和"自信的错误"的两件事：**逐条规则**评分而不是让两臂互相对着 diff，并且**盲评**——不知道某个 diff 来自哪一臂。

简版：

1. 把常驻加载文件变成一份可测试主张的编号清单。把任何不可证伪的东西（"写干净代码"）标记为恰好如此。
2. 对照每条主张评判每次运行的 diff：`followed`（遵循了）、`violated`（违反了）或 `n/a`（不适用）。
3. 然后才把判定接回各臂，读出模式。

## 第 6 步：报告

给用户一张表，每条规则一行，按可操作的行在前排序：

| 跨运行的模式 | 判定 | 行动 |
|---|---|---|
| 对照组遵循，被剥离组违反 | 关键（load-bearing） | 保留，重写得更短 |
| 双臂都遵循 | 模型本来就会这么做 | 删除 |
| 双臂都违反 | 加载了也被无视 | 改成钩子或测试，或删除 |
| 从不适用 | **未测试（untested）** | 保留，没有正反两方面的证据 |
| 臂内不一致 | 噪音 | 更多运行或更好的任务 |

把"未测试"与"无差异"在视觉上分开。它们在数据里看起来一样，含义却相反，把它们合并正是"保护了本任务从未触达的场景的规则"被删除的方式。

## 第 7 步：应用——要经过用户批准

绝不无人值守地编辑规则文件。提出编辑、展示 diff、等待。

一次只重新添加或保留一行，只针对有观察证据的规则，并优先测试、然后钩子、然后按需加载的指令，最后才是常驻加载的一行。最后重新运行 `map_layer.py`，让新的常驻加载总量与旧的并排展示。

## 给用户的诚实框架

- **一个探针任务是一个数据点，不是判决。** 在删除任何大块内容前，鼓励对代码库的另一部分做第二个任务。
- **空结果（null result）是真实结果。** 如果双臂匹配，那部分层确实已过期，可以删。
- **反过来也成立。** 不要让一次干净的运行证明删除规则是正当的——那些任务从未演练过的场景：安全、合规、发布流程。
- **现有代码会替代规则文件。** 被剥离的运行会从相邻代码复制约定——只要有一个邻居可复制。同一条规则可能在一个被编辑的文件里成立，在一个新文件里被违反。给新文件证据更高权重，并说明每个判定依据的是哪种。
- **更便宜更小的模型比前沿模型更依赖指令。** 一个在前沿模型下看起来多余的层，可能仍在承载一个更便宜的模型。如果团队混合使用，针对使用中最弱的模型做消融。

## 资源

- `scripts/map_layer.py`：该层的只读清单，与 AI 助手无关。
- `scripts/run_ablation.py`：运行双臂并收集 diffs。`--help` 列出每个标志。绝不把任一脚本读进上下文；只读它们的输出。
- `references/comparison.md`：评分标准。在第 5 步前读取它。
