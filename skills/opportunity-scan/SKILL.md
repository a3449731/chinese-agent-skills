# 机会扫描 —— 从实际发生的事中找到要改什么

读取 AI 助手自己的能力加上**你选择的一个目标**，并推荐每条发现应该变成哪个原语。**与具体 AI 助手无关**（Claude Code、Codex、PI……）。它把发现映射到**完整的原语调色板**（规则 · 技能 · 钩子 · 子代理 · MCP · 自动化/工作流），并且对**任何** AI 助手都有效，因为它先学习那个 AI 助手的能力。

**两个目标，一个技能——这就是整个设计：**
- **一次运行 → 反应式循环。** 你跑的一个循环里刚出了岔子。把扫描指向那次运行的产物，问*"AI 层里有什么本可以阻止这个？"* 你修的是系统，不是代码。
- **一段时间窗的日志 → 主动式扫描。** 什么都没坏。把它指向数周的会话，问*"有哪些我一直在手动做的事应该被编码？"*

同一个技能，同一种输出形状——你只是改变它读取的东西。

这是一个**发现**工具——*改什么*——不是质量**评估**（*建好的东西好不好*）。把两者分开。

## 输入——先是必填，然后可选

把 `$ARGUMENTS` 当作**散文**来读，而不是位置槽位。只有输入 1 是必填。输入 2 是自由文本，会含空格，所以绝不按空白拆分参数、绝不按位置绑定——不带引号输入的引导仍然是一个引导。如果有缺失，**一次、在一条消息里**问完，不要一个问题一个问题地问。

1. **扫描什么** *（必填）* —— 恰好一个：
   - **一次运行（反应式）** —— 一个循环留下的产物：计划、实施报告、RCA、PR 正文、评审输出、提交/diff。如果你指得出来，也加上那次运行的会话日志。*这些已经以运行为界，所以没有会话狩猎要做。*
   - **一段时间窗的日志（主动式）** —— 你的 AI 助手把会话日志放在哪里，加上回溯多久。示例：Claude Code → `~/.claude/projects/` + `~/.claude/history.jsonl`；Codex → `~/.codex/sessions/`；Qoder → IDE 的会话记录目录（如 `~/.qoder-cn/` 或 `~/.qoder/` 下的项目会话缓存）；PI → 你扩展的日志目录。默认窗口：最近 2 周。

   这个选择就是让扫描变成反应式或主动式的东西。其他什么都不变。
2. **你的引导** *（可选——问一次，接受"没什么特别的"）* —— 一个输入，含义随目标走：
   - **扫描一次运行：** 你**注意到的症状**，用你的话说——AI 助手哪里搞错了、你不得不纠正什么、什么惹恼了你。你在场；不要让扫描从产物里重新推导你已经能直接说出的事。*（这是单句外层循环的"你刚才做了 X"——工具化版本接受同一个 X。）* 只保留观察本身；搞清楚**为什么**发生是扫描的工作，不是你的。
   - **扫描日志：** 你**在意的主题**——你不想再手动做的那类工作、你一直在执行的质量线、循环里一直在耗你的部分。没有它，扫描只能按频率排名，那和按"对你重要"排名不是一回事。

   无论哪种：**你提供引导，目标提供证据。**
3. **AI 助手自己的能力文档** *（可选——通常你自己解决）* —— 让扫描知道你的 AI 助手*能变成什么*（它真正的扩展点）。**自己查出来；不要先问。** 识别你正在以哪个 AI 助手身份运行，找到它自己的可扩展性文档（对 Claude Code 是 `code.claude.com/docs`；对 Qoder 是它的技能/规则/子代理文档）。只有在你真的无法确定、或用户想让你指向某个特定地方时才问。绝不假设固定的扩展点集：从你实际找到的文档里读它们。

## 步骤——保持字面执行；这是最脆弱的部分（元提示词）

1. **学习你自己的能力。** 确定你以哪个 AI 助手身份运行，读取它的能力文档（输入 3，通常你自己解决）。写一份*这个* AI 助手扩展点的简短内部清单（规则、技能、钩子、子代理、MCP/工具、自动化/工作流——文档描述什么就是什么）。用文档说的——不要假设固定集合。
2. **读取目标** —— 按输入 1 是什么分支：
   - **一次运行：** **完整**读取那些产物——它们很小，细节才是重点。如果输入 2 点了症状，**从那里开始**：在产物里找到它，对照实际发生的事验证它，而不是从零重新推导用户已经告诉你的。然后重建运行的其余部分：要求了什么、AI 助手做了什么、哪里出错、哪里不得不被纠正、它假设了什么、它跳过了什么——被点名的症状是入口，不是眼罩。最后读 diff，把它当作证据而不是主题。
   - **一段时间窗的日志：** 抽出你实际做过的事——反复出现的命令、重复的多步序列、重复的指令/纠正、伸手去拿的工具、摩擦/重试。**聚合，不要吞下：** 日志可能巨大——优先用提示词/命令历史文件而不是原始转写，用 shell 工具（`jq`/`grep`/`sort | uniq -c`）缩减，让只有频率和有代表性的样本进入你的上下文，绝不整份日志。
   
   无论哪种：如果你定位不到或解析不了目标，**问用户而不是凭空编造。**
3. **找到要改什么** —— 问题随目标而不同：
   - **运行（反应式）：** 对每件出错或需要纠正的事，问**"AI 层里有什么本可以阻止这个？"** 说出本可以抓住它的**最小持久更改**——规则里的一行、技能里加的一步、一个钩子、更紧的工具作用域——具体到今天就能应用。**修系统，不是修代码：** 不要提出代码修复，要提出那个本可以让代码修复变得不必要或自动化的东西。⚠️ **不是每个失败都是系统缺口** —— 如果某件事出错而没有任何持久更改能阻止它，明说，不要为一个一次性事件发明一条规则。一句诚实的"这里没什么要改的"比五条猜测性的规则更有价值。
   - **日志（主动式）：** 对每个反复出现的模式，问**"这应该变成什么？"** 大致按（出现频率 × 编码能省多少）排序。
   
   **两个目标：** 挑选**最契合的原语**（从第 1 步的清单里），并说出*为什么*。如果给了输入 2，**给它加权**——在运行上，被点名症状的预防措施在报告中领跑（如果证据说症状其实是别的，坦率说）；在日志上，即使不是最高频的模式也要浮出用户说他们在乎的，并且坦率说出什么时候一个高频模式*不值得*编码。并且用**已有产物的自家风格**来提出每项更改：先浏览几个项目当前的规则/技能/AI 助手配置，把建议塑造成它们的样子，让建议的东西是用户真的会去建的。映射示例：
   - 你一直在重述的一条规则 → **规则**（CLAUDE.md / AGENTS.md）
   - 一个重复的多步工作流 → **技能**
   - 你一直在手动执行的一个绝不/必须 → **钩子**
   - 一个专业化的重复委托 → **子代理**
   - 一个你经常做的干净端到端交接 → **自动化**（以后：Archon 工作流）
4. **写报告**为单个自包含 HTML 文件（见下面的契约），然后告诉用户它在哪。

## 报告契约——规定如何渲染，绝不规定包含什么

**让分析驱动报告。** 有哪些章节、每章放什么、每章挖多深、有多少机会、哪些引文或数字值得抽出来——全部来自你实际找到的东西，而不是本技能。**不要**把报告框进固定章节集，**不要**预置发现，**不要**告诉它该得出什么结论。数据丰富，报告就丰富；一个发现值得一个专属的深挖章节，就给一个；有意外浮现，就浮出它。

只有**渲染**是被规定的：
- 一个**自包含的 `.html`** 文件（内联 CSS），任何浏览器都能打开。
- **视觉干净、可扫读、慷慨** —— 让发现呼吸；用最适合实际发现内容的任何布局、章节、真实引文、统计或视觉。

规则：本技能管*怎么把它放到页面上*，绝不管*页面上有什么*。

## 保持轻量
只做这四步，清清楚楚。不要添加评分框架、配置或不需要的多余环节。如果某一步无法完成（找不到文档或目标），停下并问——绝不编造分析。
**每次运行只扫描一个目标。** 如果有人想要反应式和主动式两种视图，那是两次运行、两份报告——把"这个循环里什么坏了"和"我一个月里一直在重复什么"混在一起，会产生一份两个问题都答不好的报告。
